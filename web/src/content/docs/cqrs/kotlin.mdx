CQRS (Command Query Responsibility Segregation) gives state-changing operations and read operations separate models. Registering an author is a command with the inputs needed to register them; listing authors is a query that returns a view for the reader. You can keep both in one application over one database. Neither an event store nor separate services are required.

Cratis Arc brings this model to Kotlin and Java on Spring Boot, published to Maven Central as `io.cratis:arc`. A command is an annotated class with a `handle` method, and a query is a static method on a `@ReadModel`. Kotlin Symbol Processing (KSP) generates HTTP endpoints and typed TypeScript clients at compile time, so you do not write a controller per operation. Cratis Chronicle adds event sourcing when you need a history of changes.

The examples below register and list authors using MongoDB, then show the event-returning command. If you are weighing the design before choosing a framework, read [CQRS explained](/concepts/cqrs/).

## What you get on the JVM

| Capability | How it looks in Arc | Publication |
| --- | --- | --- |
| Commands | `@Command` class with `handle`; regular, `suspend` (Kotlin) or `CompletionStage` (Java) handlers | Artifacts published |
| Queries and read models | `@ReadModel` with static or `@JvmStatic` companion query methods; GET and RFC QUERY | Artifacts published |
| Live queries | Kotlin `Flow`, JDK `Flow.Publisher` or RxJava 3 return types; SSE and WebSocket | Artifacts published |
| Validation | Jakarta Bean Validation, plus reusable Arc validators | Artifacts published |
| Authorization | `@Authorize`, `@Roles` and `@AllowAnonymous` on commands and queries | Artifacts published |
| Persistence | Spring Data JPA and MongoDB integrations | Artifacts published |
| Typed frontend | TypeScript proxies generated at build time | Artifacts published |
| Event sourcing | Chronicle through `io.cratis:cratis`; `handle` returns an event; optional | Artifacts published |

The artifacts listed above are published. Arc on the JVM does not claim full parity with Arc on .NET. The shared [capability matrix](/arc/capabilities/) and the [JVM parity reference](/arc/backend/kotlin/reference/parity/) record each row, the evidence behind it, and what is not planned. One example: Arc on the JVM generates model-bound endpoints only, not controller-based ones.

## A command and a query

`RegisterAuthor` carries the author's identifier and name as properties. Its `handle` method receives `AuthorRepository` from Spring through `@FromServices` and inserts the author. This version uses Spring Data MongoDB, with no Chronicle dependency:

<Tabs syncKey="cqrs-jvm-language">
  <TabItem label="Kotlin">
```kotlin
import io.cratis.arc.artifacts.Command
import io.cratis.arc.artifacts.FromServices
import java.util.UUID

@Command
data class RegisterAuthor(val id: UUID, val name: String) {
    fun handle(@FromServices authors: AuthorRepository) {
        authors.insert(Author(id, name))
    }
}
```
  </TabItem>
  <TabItem label="Java">
```java
import io.cratis.arc.artifacts.Command;
import io.cratis.arc.artifacts.FromServices;
import java.util.UUID;

@Command
public record RegisterAuthor(UUID id, String name) {
    public void handle(@FromServices AuthorRepository authors) {
        authors.insert(new Author(id, name));
    }
}
```
  </TabItem>
</Tabs>

The query side is a read model with a static method. Arc serves it over HTTP and generates the client types:

<Tabs syncKey="cqrs-jvm-language">
  <TabItem label="Kotlin">
```kotlin
import io.cratis.arc.artifacts.FromServices
import io.cratis.arc.artifacts.ReadModel
import org.springframework.data.mongodb.repository.MongoRepository
import java.util.UUID

interface AuthorRepository : MongoRepository<Author, UUID>

@ReadModel
data class Author(val id: UUID, val name: String) {
    companion object {
        @JvmStatic
        fun allAuthors(@FromServices authors: AuthorRepository): List<Author> = authors.findAll()
    }
}
```
  </TabItem>
  <TabItem label="Java">
```java
// AuthorRepository.java
import org.springframework.data.mongodb.repository.MongoRepository;
import java.util.UUID;

public interface AuthorRepository extends MongoRepository<Author, UUID> { }

// Author.java
import io.cratis.arc.artifacts.FromServices;
import io.cratis.arc.artifacts.ReadModel;
import java.util.List;
import java.util.UUID;

@ReadModel
public record Author(UUID id, String name) {
    public static List<Author> allAuthors(@FromServices AuthorRepository authors) {
        return authors.findAll();
    }
}
```
  </TabItem>
</Tabs>

The command inserts through `AuthorRepository`, and the query reads from it. Separating them does not mean duplicating the database: it gives the registration input and author list their own contracts. To run these excerpts, add the Gradle setup and Spring Boot application class from the [Kotlin](/arc/backend/kotlin/get-started/) or [Java](/arc/backend/kotlin/get-started/java/) getting started guide. KSP runs before compilation and reports invalid model declarations as `ARCKSP` compiler errors.

## Validation, authorization and live queries

Validation and authorization are declared on the model, not inside `handle`. Authorization annotations go on the command or read-model class or on the operation:

```kotlin
@Authorize(policy = "activeSubscription")
@Roles("member")
@Command
class UpdateProfile {
    fun handle(): Unit = Unit
}
```

An observable query returns a stream. Arc then serves the current value and each change over SSE or WebSocket. In Kotlin, return a `Flow`:

```kotlin
@ReadModel
@AllowAnonymous
data class TaskView(val id: String, val title: String) {
    companion object {
        @JvmStatic
        fun all(@FromServices repository: TaskRepository): Flow<List<TaskView>> =
            repository.observeAll()
    }
}
```

In Java, the same method returns a `java.util.concurrent.Flow.Publisher`. A source that only emits holds no current value, so a plain `GET` snapshot answers `202 Not Ready`. Kotlin uses `MutableStateFlow` and Java uses Arc's `ObservableState<T>` to hold state. The [observable queries guide](/arc/backend/kotlin/guides/observable-queries/) shows both.

## Add event sourcing with Chronicle

`io.cratis:arc` has no Chronicle dependency. When you want events as the source of truth, add `io.cratis:cratis`, the single dependency for an event-sourced Spring Boot application. Then `handle` returns the fact, and Arc appends it:

<Tabs syncKey="cqrs-jvm-language">
  <TabItem label="Kotlin">
```kotlin
import io.cratis.arc.artifacts.Command
import io.cratis.arc.artifacts.CommandKey
import io.cratis.chronicle.events.EventType

@Command
data class RegisterAuthor(@CommandKey val id: String, val name: String) {
    fun handle(): AuthorRegistered = AuthorRegistered(name)
}

@EventType
data class AuthorRegistered(val name: String)
```
  </TabItem>
  <TabItem label="Java">
```java
import io.cratis.arc.artifacts.Command;
import io.cratis.arc.artifacts.CommandKey;
import io.cratis.chronicle.events.EventType;

@Command
public record RegisterAuthor(@CommandKey String id, String name) {
    public AuthorRegistered handle() {
        return new AuthorRegistered(name);
    }
}

@EventType
public record AuthorRegistered(String name) { }
```
  </TabItem>
</Tabs>

An event-returning command needs a stable `@CommandKey` so Arc knows whose event history to append to. Without one, Arc returns a validation error and does not guess the event source. A Chronicle projection or reducer builds the read model asynchronously. The query can keep its shape, but an immediate read after the command may still return the earlier state.

Follow the [Chronicle integration guide](/arc/backend/kotlin/guides/chronicle/) to configure the starter and a compatible kernel, then run the samples. For the event store itself, see [event sourcing in Kotlin and Java](/event-sourcing/kotlin/).

## When CQRS on the JVM is worth it

Use it when reads and writes have different shapes, load or rules, when a frontend needs typed and live data, or when you may want event sourcing later without changing the query contract.

For a single form over a single table, Spring MVC with Spring Data may be enough. Separate command and query types become extra code to maintain if the two operations have no different requirements. [Coming from Spring MVC](/arc/backend/kotlin/coming-from-spring-mvc/) compares the approaches. Arc on the JVM targets Spring Boot servlet hosting and needs JDK 17; check the getting started guide for the Kotlin compiler version before adding its build tooling.

## Frequently asked questions

### Is there a CQRS framework for Spring Boot?

Yes. Arc on the JVM provides commands, queries, validation, authorization and generated TypeScript clients for Spring Boot, in Kotlin and Java. It does not claim full parity with Arc on .NET; the parity reference lists the gaps.

### Do I need Axon for CQRS in Java?

No. CQRS is a design choice. Arc handles commands and queries without an event store, over Spring Data JPA or MongoDB. Add Chronicle only if you want event sourcing.

### Can I use CQRS in Java without event sourcing?

Yes. `io.cratis:arc` has no Chronicle dependency. The same slice works over JPA or MongoDB, as the example above shows.

### Does it work from Java as well as Kotlin?

Yes. Java uses records or classes with annotations, `CompletionStage` and `Flow.Publisher` return types, and blocking bridges. Some contracts need an adapter bean in Java; the capability matrix names them.

### How does a React frontend call it?

Arc generates TypeScript proxies from the same compile-time metadata, for the same `@cratis/arc` packages used with the other backends. See [TypeScript proxies](/arc/backend/kotlin/guides/typescript-proxies/).
