## What to send where

| Feedback | Best place |
|---|---|
| "This concept confused me" | [Cratis Discord](https://discord.gg/kt4AMpV8WV), then a [Documentation issue](https://github.com/Cratis/Documentation/issues) if the docs need a change |
| "This API or workflow feels awkward" | [Cratis Discord](https://discord.gg/kt4AMpV8WV) for discussion, then the [matching product issue tracker](/community/#github-issue-trackers) |
| "The docs are missing an example" | [Documentation issues](https://github.com/Cratis/Documentation/issues) |
| "This bug is reproducible" | The [matching product issue tracker](/community/#github-issue-trackers) |
| "I found a security problem" | [Security](/security/), privately, never a public issue |
| "I have an idea for a feature" | [Cratis Discord](https://discord.gg/kt4AMpV8WV) for early shaping, then a GitHub issue when the proposal is concrete |
| "I want to understand what is planned" | [Roadmap](/roadmap/) |
| "I want to propose a larger design change" | [Governance](/governance/) |
| "I want to contribute the change" | [Contributing](/contributing/) |

If you are not sure where the feedback belongs, start in [Community and help](/community/). We can help route it.

## Product issue trackers

Use the [GitHub issue tracker table](/community/#github-issue-trackers) to find the repository for your product, client, or tool. Documentation feedback goes to [Documentation issues](https://github.com/Cratis/Documentation/issues). If ownership is unclear, ask in Discord rather than opening the same issue in several repositories.

## Useful feedback

The most useful feedback tells us what happened in context:

- What you were trying to do.
- Which product or page you were using.
- What you expected to happen.
- What happened instead, or where you got stuck.
- What would have made the next step obvious.

For documentation feedback, a short note like "I reached this page looking for X, but found Y" is enough. For product feedback, include the package version, runtime, command, API, or component involved when you know it. Leave out secrets and personal or customer data; issues and Discord threads are public.

<Aside type="tip" title="Real examples beat polished proposals">
If you can share the event, command, projection, screen, CLI command, or paragraph that caused the friction, start there. We can help turn the observation into a concrete issue or improvement.
</Aside>

## What happens next

Open feedback may stay as a conversation until the right shape is clear. Once it becomes actionable, we prefer to capture it as a GitHub issue so it has a durable record, can be linked from pull requests, and does not disappear in chat history.

An issue records the request; it does not commit the maintainers to implementing it or responding by a deadline. For questions that need an answer rather than a change, use [Community and help](/community/).
