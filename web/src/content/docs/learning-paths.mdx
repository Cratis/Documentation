Paths share pages, and you can switch at any point. If none of them fits, [Adopting Cratis](/adopting-cratis/) helps you pick a starting product first.

## New to event sourcing

**For** developers who have built CRUD applications and want to know what changes when events become the source of truth. **When you finish**, you can model a small domain as facts, explain how read models are derived from them, and say where event sourcing is the wrong tool.

1. Read [Why event sourcing](/chronicle/why-event-sourcing/) for the argument, then [CRUD, EF Core, and Chronicle](/chronicle/coming-from-crud/) to map tables and `SaveChanges` onto events.
2. Read [Event modeling](/event-modeling/). It gives you the notation the rest of the docs use for commands, events, and read models.
3. Build the [Chronicle tutorial](/chronicle/tutorial/). It adds one concept at a time to a small library domain.
4. Read [Consistency](/chronicle/concepts/consistency/) and [When to use event sourcing](/chronicle/concepts/when-to-use-event-sourcing/).
5. Bring your first real model to [Community and help](/community/). A modeling question with the business decision and the facts you already have usually gets a useful answer.

## Build a full-stack app

**For** .NET developers starting a new information system with Chronicle, Arc, and Components together. **When you finish**, you have a running application with one slice you wrote yourself, and you know where the command, event, projection, query, and screen for a feature live.

1. Follow [Build a full-stack feature](/build-a-full-app/). It scaffolds an application from the Cratis template and adds one slice end to end.
2. Read [Vertical slices](/arc/vertical-slices/) to see why the feature lives in one folder.
3. Work through the [Arc tutorial](/arc/tutorial/) for validation, related slices, live queries, and authorization. It runs over a plain database, which keeps the focus on commands, queries, and generated proxies.
4. Read [Add event sourcing to an Arc slice](/arc/backend/csharp/chronicle/add-event-sourcing/) to see what changes when a slice's writes move to Chronicle, and what does not.
5. Continue with the [vertical slices scenario](/scenarios/vertical-slices/) for the state view, automation, and translation patterns, and [Testing with Cratis](/testing-with-cratis/) for specs.
6. Follow [Generated values, from Screenplay to running app](/generated-values/) to have the server own your ids and secrets, from the model through Stage and Arc to pinned specs.

Building on Kotlin or Java instead? The [Cratis Kotlin](/templates/cratis-kotlin/) and [Cratis Java](/templates/cratis-java/) templates scaffold the same full-stack shape on Spring Boot, and the Arc tutorial shows its main slice examples in Kotlin as well as C#. Some backend snippets are C# only.

## Write-side consistency

**For** developers who write commands whose outcome depends on stored state: a stock level, a limit, a capacity, a document someone else may edit. **When you finish**, you can say why a plain read does not hold a rule, pick the mechanism that does, write a protected command, and test that it holds when two requests race. Arc read protection needs Arc 22.106.0 or later, which uses Chronicle 19.71.0 or later.

1. Read [Keeping decisions correct](/concepts/keeping-decisions-correct/). It is the five-minute introduction: why a read model can be stale at write time, what read protection does, and which mechanism holds which rule. If you know DCB, KurrentDB, Marten or Axon, read [Read this first](/concepts/read-this-first-write-side-consistency/) next.
2. Follow [Getting started with read protection](/arc/backend/csharp/chronicle/consistency/getting-started/) to write your first protected command and see the error the losing request gets. Using Chronicle without Arc? Start from [Decision reads](/chronicle/read-models/decision-reads/) instead.
3. Work through the scenarios from simple to advanced. Each has the rule, the code and the guard it produces.
   - [One entity](/arc/backend/csharp/chronicle/consistency/scenarios/single-entity/): stock on one book.
   - [Unique and once](/arc/backend/csharp/chronicle/consistency/scenarios/unique-and-once/): constraints, no read needed.
   - [Two entities](/arc/backend/csharp/chronicle/consistency/scenarios/two-entities/): a loan limit and a course capacity.
   - [One stream](/arc/backend/csharp/chronicle/consistency/scenarios/per-stream/): a monthly limit, with a per-stream read model.
   - [Process stream](/arc/backend/csharp/chronicle/consistency/scenarios/process-stream/), [gapless numbers](/arc/backend/csharp/chronicle/consistency/scenarios/numbering/), [rich aggregate](/arc/backend/csharp/chronicle/consistency/scenarios/aggregate/) and [editing conflict](/arc/backend/csharp/chronicle/consistency/scenarios/editing-conflict/).
   - [Test the race](/arc/backend/csharp/chronicle/consistency/scenarios/testing/) to prove a rule holds. For the Chronicle client, see the [Chronicle scenarios](/chronicle/dynamic-consistency-boundary/scenarios/).
4. Adopt it in an existing application with [Adopting read protection](/arc/backend/csharp/chronicle/consistency/adopting/): `Off`, then `Measure`, then `On`.
5. Walk the whole stack in [Decisions that hold, from model to frontend](/decisions-that-hold-walkthrough/): one rule from a Screenplay model to an Arc command under read protection, a spec that makes the race happen, and a frontend that handles a lost race. For the idea behind it, read [The Dynamic Consistency Boundary](/concepts/dynamic-consistency-boundary/).
6. Keep the reference close: [Reads](/arc/backend/csharp/chronicle/consistency/reads/), [Validators](/arc/backend/csharp/chronicle/consistency/validators/), [Refusals](/arc/backend/csharp/chronicle/consistency/refusals/), [Pitfalls](/arc/backend/csharp/chronicle/consistency/pitfalls/) and the [FAQ](/arc/backend/csharp/chronicle/consistency/faq/). For the mechanics, read [How guards are derived](/chronicle/dynamic-consistency-boundary/how-guards-are-derived/) and [Read protection in Chronicle](/chronicle/read-models/read-protection/).

## Use Chronicle from another language

**For** developers whose services are not written in .NET. **When you finish**, your service appends events to Chronicle and a projection or reactor responds to them.

1. Read [Chronicle in your language](/chronicle-clients/) to see which clients are published and where each is documented.
2. Start a local kernel and follow the shared loop on [Chronicle getting started](/chronicle/get-started/). Its examples have a tab for each client that implements them.
3. Follow your client's setup guide: [TypeScript](/chronicle/clients/typescript/getting-started/), [Kotlin and Java](/chronicle/clients/kotlin/get-started/), or [Elixir](/chronicle/clients/elixir/get-started/).
4. Build the [Chronicle tutorial](/chronicle/tutorial/) and pick your client's tab where one exists.

The Python client is pre-release and not published yet; [Event sourcing in Python](/event-sourcing/python/) tracks it.

## Evaluate Cratis

**For** architects and team leads deciding whether to adopt Cratis. **When you finish**, you can name the product you would start with, the first slice you would move, and the version and production questions you still need answered.

1. Read [Why developers choose Cratis](/why-cratis/), including when it is not a good fit.
2. Read [Adopting Cratis](/adopting-cratis/) to pick an entry point for a new or existing system.
3. If you are comparing event stores, read [Compare event sourcing for .NET](/compare-event-sourcing-dotnet/) or [Compare event sourcing on the JVM](/compare-event-sourcing-jvm/). [Marten vs Chronicle](/compare/marten-vs-chronicle/) is a head-to-head for .NET teams on PostgreSQL.
4. Check the [FAQ](/faq/), [Version compatibility](/compatibility/), and [Production readiness](/production-readiness/).
5. Run one [sample](/samples/) that matches the shape you would build.
6. Ask adoption questions in [Community and help](/community/), or [Work with us](/work-with-us/) for a dedicated review.

## Operate Chronicle

**For** people who deploy and run Chronicle. **When you finish**, you can host Chronicle with storage and TLS you chose deliberately, find a failed partition, and plan an upgrade.

1. Read [Chronicle hosting](/chronicle/hosting/) and [Production hosting](/chronicle/hosting/production/).
2. Review [Chronicle configuration](/chronicle/hosting/configuration/), including [storage](/chronicle/hosting/configuration/storage/).
3. Learn the [CLI](/cli/) and the [Workbench](/chronicle/workbench/), then keep [Chronicle troubleshooting](/chronicle/troubleshooting/) close.
4. Use [Production readiness](/production-readiness/) as the cross-stack checklist.
5. Before each upgrade, use [Plan an upgrade](/upgrade-path/) and [What's new](/whats-new/). Follow [Security](/security/) for vulnerability reporting.

## Frontend developer

**For** React developers joining a team that already has an Arc backend. **When you finish**, you can call commands and queries through generated proxies and build forms, dialogs, and live tables with Components.

1. Read [Understanding the proxy boundary](/arc/understanding-the-proxy-boundary/) to see where the generated TypeScript comes from and why you never edit it.
2. Read [Arc frontend](/arc/frontend/).
3. Build the [Components tutorial](/components/tutorial/), then use [Choosing a component](/components/choosing-a-component/) for new screens.
4. Browse [Storybook](/components/storybook/) for live examples. Coming from PrimeReact? Read [Coming from PrimeReact](/components/coming-from-primereact/).
5. Run a [sample](/samples/) with a React frontend to see the screen and backend together.

## Contributor

**For** people changing Cratis itself. **When you finish**, you know where a change belongs and what a pull request needs before review.

1. Read [Contributing](/contributing/) and [Governance](/governance/).
2. Find the repository that owns the behavior. Product pages are written in each product repository's `Documentation/` folder; only site-level pages such as this one live in the Documentation repository.
3. Use [Feedback and suggestions](/feedback/) or Discord for early ideas before opening a large proposal.
4. Run the owning repository's build, specs, and documentation checks before opening a pull request.
