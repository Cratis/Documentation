Use the Cratis AI managed install to keep your team's guidance with the code.
Committing the installed files and configuration gives developers and CI the
same source guidance, with updates they can review as repository changes.

## What you do

Install the [Cratis CLI](/cli/getting-started/) first. Run `cratis ai install`
in the repository root and select the harnesses (coding tools), profiles
(guidance sets), and languages the repository needs. Review and commit the
result. The [setup guide](/ai/getting-started/) walks through the selection and
how to check that your tool can find the installed skills.

| Path | What it carries |
| --- | --- |
| `.cratis/ai.json` | The selected harnesses, profiles, and languages. |
| `.cratis/ai/` | Cratis-managed rules, skills, prompts, agents, and hooks, plus anything you add. |
| `.cratis/ai.manifest.json` | The source revision, managed file identities and hashes, and owned integrations. |
| Harness adapters | Native links and configuration that connect each tool to the shared guidance. |

A configuration can select more than one harness and profile. This example
selects C# application guidance and documentation guidance for three tools:

```json
{
  "schemaVersion": "1.0",
  "harnesses": ["claude", "codex", "pi"],
  "profiles": ["cratis/application/csharp", "cratis/documentation"],
  "languages": ["csharp", "typescript"]
}
```

## What you get

Harness integrations use the shared `.cratis/ai` corpus instead of separately
maintained skill folders. Each tool still loads guidance through its own
integration; sharing the files does not make agent behavior identical.

Before updating, run `cratis ai update --dry-run` and review the proposed
changes. Commit the configuration, manifest, corpus, and adapters together so
the next checkout carries a consistent installation. The manifest records the
installed revision but does not pin future updates; use
[updates and rollback](/ai/scenarios/updates-and-rollback/) to choose a fixed
source or return to an earlier revision.

Keep repository-specific guidance in `.cratis/ai/rules/project.md` and its
concern files, and add your own skills under `.cratis/ai/skills/` with names
that do not start with `cratis-`. These remain yours. Editing a managed file
instead blocks update and uninstall until you resolve the conflict.

To catch hand edits to managed guidance in CI, run `cratis ai status`; it exits
non-zero when a managed file was modified. By default, status and update fetch
the source corpus, including for a dry run. For offline use or a fixed source,
pass `--source <path>` to a local `Cratis/AI` checkout at the intended revision.

<Aside type="note" title="Resolving a modified managed file">
Run `cratis ai status` to see which paths changed. Keep a local adaptation in
a project-owned file, or propose a reusable improvement to `Cratis/AI`. Restore
the managed file before updating, or use `cratis ai update --force` or
`cratis ai uninstall --force` only when you deliberately want to replace or
remove its edited content. Force does not bypass ownership checks or resolve a
changed Model Context Protocol (MCP) server registration.
</Aside>
