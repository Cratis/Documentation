Cratis AI has a canonical corpus of reusable **rules** and **skills**. Rules are
always-on repository guidance; skills are focused task workflows. Your repository
selects the Cratis profiles, languages, and harnesses it needs.

## Complete repository setup

Install the Cratis CLI, then run this from the repository root:

<Steps>

1. Run `cratis ai install`.
2. Select one or more harnesses, profiles, and languages when prompted.
3. Commit `.cratis/ai.json`, review the generated `.cratis/ai` content, and run your
   normal repository checks.

</Steps>

For automation, provide the selections explicitly:

```bash
cratis ai install \
  --harnesses claude,cursor,opencode,pi \
  --profiles cratis/chronicle,cratis/arc \
  --languages csharp,typescript
```

The command reads the AI repository's `.cratis/ai/manifest.json` first, so the
interactive choices always reflect the harnesses, profiles, and languages that
the corpus currently offers. It then records the selection in `.cratis/ai.json`,
resolves the matching corpus, installs only Cratis-managed files under `.cratis/ai`, and
configures each selected harness. Pi receives native `.pi` agents, prompts, skills,
and extensions in addition to the shared repository instructions; Cursor and
OpenCode receive their native project folders. No harness decides which profiles
or languages apply.

<Aside type="note" title="Your files remain yours">
Every installed text file carries a `cratis-ai-managed` marker and is recorded
with its installed hash. Add your own rules and skills anywhere under `.cratis/ai`.
An update or uninstall stops before changing anything when a managed file hash no
longer matches. Review the reported paths, or explicitly use `--force` to replace
or remove the modified managed files.
</Aside>

## Maintain the installation

```bash
cratis ai status
cratis ai update
cratis ai uninstall
cratis ai update --force
```

`status` shows selections, installed corpus information, and local conflicts.
`update` adds, changes, moves, and removes only unchanged Cratis-owned content;
both commands stop before any change when they find a modified managed file.
Use `--force` only after reviewing the conflict; it deliberately replaces or
removes modified managed content. `uninstall` otherwise preserves it and all
user-owned files.

## Choose the integration that fits your repository

### Managed by Cratis

Use `cratis ai install` when a repository uses multiple harnesses or wants one
reviewable source for shared guidance. The CLI resolves the selection, writes
managed rules and skills into `.cratis/ai`, creates harness links, and records
hashes in `.cratis/ai.manifest.json`. Pi is configured directly by the CLI; it
does not require the Pi package. Update and uninstall stop on local changes
unless you explicitly pass `--force`.

You keep full control: add, edit, or delete your own content under
`.cratis/ai`. Only paths recorded in the manifest are Cratis-managed.

### Native plugin or marketplace

Use a harness plugin when you want the familiar, harness-specific path instead.
For example, `pi install -l npm:@cratis/pi` installs the Pi integration. It reads
`.cratis/ai.json`, resolves only the selected Pi skills, and contributes the
packaged Cratis rules and prompts through Pi's extension APIs. Without a
configuration file it exposes the complete packaged skill set. This path is
intentionally independent of the CLI.

A plugin gives one harness configuration-aware packaged content, but not the
complete **multi-harness managed lifecycle**. It does **not** create a shared
local corpus, configure other harnesses, install every harness-specific artifact,
or provide managed update/uninstall hash protection. In a single-harness
repository, add your own rules, agents, prompts, and skills directly in that
harness's normal folder exactly as you do today; `.cratis/ai` is optional unless
you choose the managed path.

## Contribute and verify skills

Skills may include executable verification scenarios. The verification runner
discovers them, applies deterministic assertions, and emits a pass/fail report
locally and in CI. Verification answers whether a skill behaves as intended;
it is not an authorship or provenance gate.
