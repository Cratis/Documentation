[Chronicle](/chronicle/) directly.

## Design before you build

Teams often write the code first and discover the domain afterwards. By the
time everyone agrees on what "an order" is, half of it has been built around a
different idea. Event modeling turns that around: you map out *what happens* in
the system as a shared picture before anyone commits to an implementation.

Studio is meant to be the canvas for that conversation, where developers, domain
experts, and product owners work on the same model instead of trading
diagrams.

## What Studio works with

Rendering a model into a running application is [Stage](/screenplay/faq/#what-are-stage-and-studio)'s
job. Stage remains experimental, so treat generated output as
something to review, not as finished production code.

## Where it fits

Studio is an **independent top layer**. You can use it to model an event-driven
system without adopting the rest of the stack. With the Cratis Stack, the model
describes the commands, events, and projections you build with
[Arc](/arc/) and [Chronicle](/chronicle/).

<StackDiagram current="studio" />

Studio sits at the *front* of development: design and agree on the model there,
then build. To *inspect and operate* a system that is already running, use the
[CLI](/cli/) and the Chronicle Workbench.
