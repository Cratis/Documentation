Studio is a shared place to design, visualize, and edit [Screenplay](/screenplay/) event models: the commands people issue, the events they produce, and the read models people look at. Follow its progress at [cratis.studio](https://cratis.studio).
</TopicHero>

<Aside type="caution" title="Experimental">
Studio is part of the Cratis model-first layer (Studio, Screenplay, Stage, Scene,
and Prologue), which is experimental and in early development. Features,
formats, and behavior can change between releases. Do not plan production work
around it yet; the stable path today is building with [Arc](/arc/) and
[Chronicle](/chronicle/) directly.
</Aside>

## Design before you build

Teams often write the code first and discover the domain afterwards. By the
time everyone agrees on what "an order" is, half of it has been built around a
different idea. Event modeling turns that around: you map out *what happens* in
the system as a shared picture before anyone commits to an implementation.

Studio is meant to be the canvas for that conversation, where developers, domain
experts, and product owners work on the same model instead of trading
diagrams.

## What Studio works with

<CardGrid>
    <Card icon="random" title="Event brainstorming">
        Boards for a digital Event Storming session: collect ideas and find the
        events that drive your domain.
    </Card>
    <Card icon="list-format" title="Event models">
        Commands, events, and read models organized into modules, features, and
        slices, stored as a Screenplay model.
    </Card>
    <Card icon="puzzle" title="Projections">
        Which events feed which read model, visible in the model itself.
    </Card>
    <Card icon="comment-alt" title="Agents over MCP">
        An organization's agents can read and change its event models through
        Studio's own MCP server.
    </Card>
</CardGrid>

Rendering a model into a running application is [Stage](/screenplay/faq/#what-are-stage-and-studio)'s
job. Stage is part of the same experimental layer, so treat generated output as
something to review, not as finished production code.

## Where it fits

Studio is an **independent top layer**. You can use it to model an event-driven
system without adopting the rest of the stack. With the Cratis Stack, the model
describes the commands, events, and projections you build with
[Arc](/arc/) and [Chronicle](/chronicle/).

<StackDiagram current="studio" />

Studio sits at the *front* of development: design and agree on the model there,
then build. To *inspect and operate* a system that is already running, use the
[CLI](/cli/) and the Chronicle Workbench.

## What you can use today

- Follow Studio's progress at [cratis.studio](https://cratis.studio).
- Write a model as text with [Screenplay](/screenplay/getting-started/), which
  Studio edits. It is experimental as well.
- New to event modeling? Read [Event modeling](/event-modeling/) and work
  through the [Chronicle tutorial](/chronicle/tutorial/).
- Model the Cratis way by hand with [vertical slices](/arc/vertical-slices/) and
  [modeling events](/chronicle/concepts/modeling-events/).
