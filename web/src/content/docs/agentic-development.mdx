An AI coding agent changes a borrowing rule. Before accepting the diff, you need to know which behavior it changed and whether two callers can still borrow the last copy at once. A passing build alone cannot answer that question.

Agentic development means giving an AI agent work such as reading code, making changes, or diagnosing a system, while a person sets direction and reviews the result. In a Cratis event-sourced application, named events record what happened, commands express intended actions, and executable specifications check examples of the rules. Those artifacts give both the agent and the reviewer evidence beyond the generated diff.

Use this guide to set up that workflow around one feature. The borrowing specification below is a concrete starting point; the later sections cover store inspection, repository conventions, and operations that need separate approval.

<Aside type="note" title="Tools and boundaries">
The [Cratis Stack](/cratis-stack/) page maps each tool to its role. You can start with specifications and read-only inspection without adopting every tool. Studio provides collaborative event modeling; Stage generates code from supported Screenplay models. Both generated code and models proposed by Prologue need human review.
</Aside>

## What an agent needs to understand a change

A coding agent works from repository files, instructions, and whatever systems it may query. If all it sees is a current database row, it may know the value without knowing which action produced it or why the business permits it. The reviewer faces the same gap.

A create-read-update-delete (CRUD) application can supply that context through audit history, explicit operations, and tests. Event sourcing takes a different approach: the stored events are the history from which state is derived. Commands name intended actions, and specifications describe expected outcomes.

That history helps only when the events carry the facts you need and the specifications cover the rule being changed. It does not capture unrecorded intent or prove that an agent understood the domain. Keep domain questions in the review rather than asking the agent to guess.

If you are new to the idea, [what is event sourcing](/concepts/event-sourcing/) covers the basics, and [coming from CRUD](/chronicle/coming-from-crud/) maps the concepts you already use.

## Events, commands and specifications as a contract agents can read

Three artifacts carry the contract in a Cratis application. Each is plain code in the repository, so an agent reads it the same way it reads any other source file.

| Artifact | What it states | Why it helps an agent |
| --- | --- | --- |
| Command | One intention a caller can express, with its inputs, validation and the events it may record | The agent can trace the inputs and expected events for an operation |
| Event | A recorded fact, named in the past tense (`BookBorrowed`), kept in the append-only history | The agent can inspect the facts used to derive state |
| Specification | A Given/When/Then example: facts that already happened, the action, the expected outcome | The agent can check an example of the required behavior |

Given/When/Then maps one to one onto event sourcing. The given is the events that already happened, the when is the command or event under test, and the then is the events, read models or side effects that result. That is why a specification reads in the vocabulary of the event model, and why a domain expert can check it without reading the implementation. [Testing with Cratis](/testing-with-cratis/) shows the mapping in C#, Kotlin, Java and TypeScript, and [Specifications](/specifications/) documents the `Establish()`, `Because()` and `Destroy()` lifecycle.

Here is a real specification from the [Decisions that hold](/decisions-that-hold-walkthrough/) walkthrough. It checks a rule that is easy to get wrong: two callers borrow the last copy of a book at the same time.

```csharp
public class when_the_last_copy_is_borrowed_concurrently : Specification
{
    static readonly ISBN _isbn = new("978-0316389704");
    readonly CommandScenario<BorrowBook> _scenario = new();
    CommandResult _result;

    void Establish()
    {
        _scenario.Given.ForEventSource(_isbn).Events(new BookAddedToInventory("The Last Wish", AuthorId.New(), 1));
        _scenario.AppendConcurrently(_isbn, new BookBorrowed(_isbn, "The Last Wish", MemberId.New(), DateTimeOffset.UtcNow, DateTimeOffset.UtcNow.AddDays(21)));
    }

    async Task Because() => _result = await _scenario.Execute(new BorrowBook(_isbn, MemberId.New()));

    void Destroy() => _scenario.Dispose();

    [Fact] void should_not_succeed() => _result.ShouldNotBeSuccessful();
    [Fact] void should_report_a_conflict() => _result.ShouldHaveValidationErrorBecauseOf(ValidationResultReason.ConcurrencyViolation);
    [Fact] void should_append_nothing() => _scenario.AppendedEvents.Count.ShouldEqual(0);
}
```

The scenario seeds one copy, so the validator sees one available copy and passes. A competing `BookBorrowed` is appended after the command reads and before it commits. The command is refused with a concurrency violation and appends nothing. The spec runs in process, without a Chronicle server or a database, so an agent can run it after every change.

When changing `BorrowBook`, keep these assertions as well as the implementation in view. If the agent makes the command succeed by weakening the conflict check, this scenario should fail. Review any change to the assertions themselves: a passing spec can still encode the wrong rule.

## Event models as the shared source for humans and AI

Contracts are cheaper to agree on before the code exists. [Event modeling](/event-modeling/) lays a system out as a timeline of screens, commands, events and read models. Because each step is named and typed, a model is a description an agent can read, and a plan a human can review before any code is written.

Cratis puts the model in a file. [Screenplay](/screenplay/) is a declarative `.play` language for one bounded context: its events, commands, queries, projections, screens and rules. [Studio](/studio/) is the collaborative environment for editing Screenplay models. [Stage](https://github.com/Cratis/Stage) compiles Screenplay, verifies supported specifications declared in the model, and renders a reviewable Arc and Chronicle application on disk.

Review the model before asking the agent to extend the generated application. The team can discuss a named command, the events it records, and the read model a screen needs without first interpreting an implementation diff. Stage's verification covers the modeled behavior it supports; review the rendered code and its specifications too.

The [event model is also the test](/event-modeling/): one column of a model becomes the Given/When/Then rows of a specification, as the [testing guide](/testing-with-cratis/#the-event-model-becomes-the-spec) shows step by step.

If you already use [EventModelers.ai](/eventmodelers-ai/), its Build Kits give an agent a model-to-code path for C#, Kotlin and Java. The page [EventModelers.ai](/eventmodelers-ai/) explains what a Build Kit does and how to pick one.

## Letting agents inspect the runtime: Chronicle MCP and the CLI

A specification covers behavior you thought of. Production shows the rest. An agent that is asked "why is this order cancelled?" or "why is this projection behind?" should read the system, not infer from the code.

Cratis gives the agent two documented routes into a running [Chronicle](/chronicle/) store.

### The Chronicle MCP server

The [Chronicle MCP server](/chronicle-mcp/) speaks the [Model Context Protocol](https://modelcontextprotocol.io). It runs over stdio as the `cratis/chronicle-mcp` container image and connects to a running Chronicle server. Releases are also listed in the official MCP Registry as `io.github.Cratis/chronicle-mcp`. Because it talks to Chronicle directly, it works with every Chronicle client language: .NET, TypeScript, Kotlin/Java and Elixir.

It exposes two kinds of tools:

- **Operate-side tools** inspect a live store: `list_event_types`, `get_events`, `get_tail_sequence_number`, `list_observers`, `list_failed_partitions`, `list_jobs` and others.
- **Design-time tools** turn a request into a reviewable proposal: describe an event type, build an event catalog, find event types nothing consumes, run an ad-hoc projection, and scaffold a read model.

The design-time tools follow one rule: introspect the store before generating anything. Field names, types and event names come from the schema registered with Chronicle, not from the model's memory. When a requested event type is not registered, the tool says so and does not invent a shape.

The tool that most directly answers the audit question is `explain_causal_trace`. It reads the ordered events of one event source together with each event's correlation id and causation chain, so the agent can say what happened and why. The documentation calls it the equivalent of `git blame` for state.

A minimal configuration for an MCP host that runs the server through Docker looks like this (taken from the [Chronicle MCP getting started](/chronicle-mcp/getting-started/) guide):

```json
{
    "servers": {
        "Chronicle": {
            "type": "stdio",
            "command": "docker",
            "args": [
                "run",
                "-i",
                "--rm",
                "-eCratis__Chronicle__Mcp__ConnectionString=chronicle://host.docker.internal:35000",
                "cratis/chronicle-mcp"
            ]
        }
    }
}
```

### Read-only by default

The server starts in the `ReadOnly` profile. In that profile the tools that change job state (`stop_job`, `resume_job` and `delete_job`) are not in the tool list and cannot be called. The `Mutation` profile exposes them, and it refuses to start unless the deployment names a principal, an expiry in the future and explicit grants for each store, namespace, operation and target. Operation wildcards are invalid, so a new mutating tool is never granted by accident. Chronicle stays the authority and applies its own authentication and authorization to every call. See [deployment profiles](/chronicle-mcp/deployment-profiles/).

<Aside type="caution" title="Local defaults">
Without configuration the server uses Chronicle's development credentials and `localhost:35000`. Those defaults are for a local development store. Give the server real credentials before you point it at a shared store.
</Aside>

### The CLI

The [Cratis CLI](/cli/) covers the same ground from a terminal and is the better fit for agents that run shell commands. Running `cratis init` in your project writes a `CHRONICLE.md` that lists every command the CLI can run, adds instruction files for the AI tools it detects, and adds a `chronicle-diagnose` slash command. The CLI can also replay an observer, which rebuilds a read model; read [replay rebuilds read models](#replay-rebuilds-read-models) before an agent runs it.

Neither route changes the event log. Both read it and operate observers and jobs; job control and replay change read-side state, so they need care and, over MCP, an explicit policy. To change state, the system goes through commands and events, so the history stays honest.

## Rules and skills that teach agents the conventions

An agent unfamiliar with Cratis may add handler classes where the framework expects a command, or hand-write an API client that proxy generation already supplies. [Cratis AI](/ai/) provides repository rules, skills, prompts, and subagents so the agent can follow those conventions. The vertical-slice layout keeps a feature's command, query, and related code together.

The main path installs the corpus into a repository with the CLI:

```bash
cratis ai install
```

Run without options it asks what the repository needs. To script it, select the harnesses, profiles and languages explicitly:

```bash
cratis ai install \
  --harnesses claude,codex,copilot,cursor,opencode,pi \
  --profiles cratis/application \
  --languages csharp,typescript
```

The CLI installs the managed content under `.cratis/ai`, creates native adapters for each selected coding tool, and records hashes in `.cratis/ai.manifest.json`. It refuses to overwrite files you own, and `cratis ai status` shows what is installed and whether a newer revision is available. Two other channels exist: the `@cratis/pi` package for Pi, and marketplace plugins for Claude Code, Codex, GitHub Copilot and Cursor, which deliver skills only. [Trust and distribution](/ai/trust-and-distribution/) explains how each channel is versioned, and the [harness guide](/ai/harnesses/) has the command for each tool.

Some of what the corpus contains, by name:

- The `new-vertical-slice` prompt scaffolds a feature: command, events, projection, query, React and specs.
- Skills such as `cratis-arc-command`, `cratis-chronicle-read-model` and `cratis-chronicle-projection` build one artifact by convention.
- The `write-specs` prompt and the `cratis-code-review` skill cover a feature with BDD specs and review it against the project's standards.

Rules and skills do not prove a change is correct. They make the first attempt look like the rest of the codebase, so review and specifications spend their time on behavior instead of style. The [code-analysis rules](/code-analysis/) enforce the same framework contracts during the build, whoever wrote the code.

One practical limit applies to every agent: a large profile such as `cratis/full` can exceed the budget some agents give to skill descriptions, so install the profiles a repository needs rather than everything.

## Guardrails: specifications, review and replay

Check an agent-written change at more than one boundary. A build can catch a contract error, but it cannot decide whether the requested business rule is right. Use specifications, append-time checks, and human review for those different questions.

| Layer | Mechanism | What it catches |
| --- | --- | --- |
| Build | [Code-analysis rules](/code-analysis/) and typed commands, events and concepts | Contract mistakes before anything runs |
| Specifications | In-process Given/When/Then scenarios for commands, read models and reactors | A behavior change the spec did not expect |
| Constraints | Rules Chronicle checks when an event is appended, such as uniqueness, and append conditions for decisions that depend on state | A change that is accepted by the code but violates a rule under concurrency |
| Review | A human reads the model, the specs and the diff | Wrong intent that a green build cannot see |

### Specifications as the first gate

Specifications give an agent a fast loop. It changes the code, runs the specs and reads the failure. Because specs are written in the language of events, a failing spec names the fact that was expected and the fact that happened. [Testing with Cratis](/testing-with-cratis/) lists the in-process scenarios for each side: command scenarios for the write side, read-model scenarios for projections and reducers, and reactor scenarios for side effects.

Specifications check the examples they express. The first review question is therefore whether those examples describe the behavior you want. An agent can write a spec that passes and asserts the wrong thing. Review the specification diff as carefully as the implementation diff, and prefer specifications written or approved from the event model.

### Constraints and decisions at append time

Some rules cannot be checked by a unit spec alone, because they depend on what other callers do at the same moment. Chronicle checks constraints when an event is appended and rejects the append if the rule fails. For decisions that read state, it can check the state the decision was based on: if a matching event was written since, the append is refused. The [keeping decisions correct](/concepts/keeping-decisions-correct/) page explains the model. This matters for agents because the rule is enforced where the data is written, not only where the agent happened to remember it.

### Replay rebuilds read models

The log also makes read models disposable. When you change how a projection or reducer builds a read model, you do not migrate the read model: you replay the observer and it rebuilds from history. The CLI does this with the `observers replay` command, and `replay-partition` does it for a single event source. The [replay a projection](/cli/scenarios/replay-a-projection/) scenario walks through it.

Replay is an operation, not a check. The event log is untouched, but the observer discards its accumulated state and rebuilds from sequence zero, so the read model is unavailable or incomplete while it catches up. Run it deliberately, after the changed projection is deployed, and prefer `replay-partition` when only one event source is affected. Specifications are the pre-deployment check: they run in process against seeded events and touch no store. Reactors need extra care, because Chronicle's .NET client replays them unless the class is marked `[OnceOnly]`; read the [reactor replay rules](/chronicle/clients/where-the-clients-differ/#reactor-replay-and-delivery-identity) before replaying one.

### Review stays human

Nothing here removes the reviewer. It changes what the reviewer reads: an event model and a set of specifications that state intent, plus a diff that has already passed the build and the specs. The record that remains after a change is the log itself. Each event carries correlation, causation and identity, so a later audit can follow a state back to the command that caused it.

## Brownfield: start from signals with Prologue

Most teams are not starting from nothing. The expensive step in moving an existing system to this way of working is the event model: someone has to read years of accreted code and write down what the system does.

[Prologue](/prologue/) adds observed evidence to that step. It stands beside the running system, without application code changes, and watches selected signals: state-changing HTTP requests, which tables and columns changed after each one, and the telemetry the system already emits. It correlates these into captures, and the Interpreter proposes modules, features and slices with candidate commands, events, read models and projections. It produces a structured result and a draft [Screenplay](/screenplay/) file.

Treat the output as another input to human modeling, not a recovered specification. Prologue records no database row values and no HTTP request or response bodies, but endpoint paths, changed column names and telemetry attributes can still be sensitive, so minimize access and protect the capture files. It cannot see a rule the system enforces without leaving a trace. It is the wrong tool for a greenfield system, for a system with no HTTP or database write path to observe, and for data migration. See [why Prologue](/prologue/why-prologue/) for the full list.

## Tools and their limits

The [capability map](/cratis-stack/) shows how these tools fit together.

| Part | Role in this practice |
| --- | --- |
| Chronicle, Arc, Specifications | Event store, application framework and spec library |
| Chronicle MCP server | Agent access to a running store, read-only by default |
| CLI | Inspection, diagnosis and `cratis ai install` |
| Cratis AI | Rules, skills, prompts and agents installed into a repository |
| Studio | Paid product for collaborative design of Screenplay event models |
| Screenplay | The `.play` modeling language |
| Stage | Compiles Screenplay, verifies supported modeled specifications, renders reviewable application code |
| Prologue | Proposes an event model from an existing system for human review |

Stage verifies supported modeled specifications, not every Screenplay construct. Check its supported behavior before treating a model as executable coverage.

By default, `cratis ai install` reads the current `main` of the Cratis AI repository. To use a fixed revision, point `--source` at a checkout of a known commit. Install only the profiles the repository needs.

These mechanisms give you evidence to review; they do not make an agent correct. Keep the human review step, including a check that the specifications still express the intended rule.

For governed agent work beyond repository conventions, [Cratis Direct](/direct/) coordinates engineering journeys with gates and review. It is a separate product from the Cratis AI guidance installed by the CLI, and access requires an enabled account.

The [roadmap](/roadmap/) and [what's new](/whats-new/) track movement on these.

## Frequently asked questions

### What does "agentic development" mean here?

It means an AI agent does a meaningful share of the work: reading the codebase, writing changes, running the checks and diagnosing a running system, with a person setting direction and reviewing. On this page it is paired with event sourcing because the log, the commands and the specifications give the agent explicit things to read and verify.

### Why does event sourcing help AI coding agents?

Events let an agent inspect the recorded facts behind state. Commands make intended actions explicit, and specifications check examples of the behavior you expect. Those contracts reduce guesswork, but only for the facts you record and the rules your specifications cover.

### Do I have to use Cratis to do this?

No. The practice does not depend on one product: a typed command model, an append-only log and executable specifications work with other tools. Cratis supplies one integrated set, from the event store and framework to the rules, specifications and MCP server. For a comparison of event stores, see [event sourcing in .NET](/compare-event-sourcing-dotnet/) and [on the JVM](/compare-event-sourcing-jvm/).

### Which coding agents does Cratis AI support?

The managed install targets Claude Code, Codex, GitHub Copilot, Cursor, OpenCode and Pi. Marketplace plugins cover Claude Code, Codex, GitHub Copilot and Cursor with skills only. The [harness guide](/ai/harnesses/) has the command for each.

### Can an agent change my production data through the MCP server?

Not by default. The server starts read-only and exposes no tool that changes state. The `Mutation` profile adds job control (stop, resume, delete) behind an explicit, time-limited policy. Application state changes only through commands and events, never through the MCP server.

### Does the MCP server work with my Chronicle client language?

Yes. It connects to the Chronicle server over gRPC, so it works with the .NET, TypeScript, Kotlin/Java and Elixir clients alike. A running Chronicle server is required.

### Where do I start?

Install the rules and skills with `cratis ai install`, connect the MCP server or run `cratis init`, and build one slice by following [build a full-stack feature](/build-a-full-app/). Then read the [Decisions that hold](/decisions-that-hold-walkthrough/) walkthrough to see a rule enforced from model to specification to frontend. [Start using Cratis AI](/ai/getting-started/) covers the first step in detail.

### How do I stop an agent from writing specs that pass but assert the wrong thing?

Treat the specification diff as the main review artifact, and derive specs from the event model. A spec should read as a sentence a domain expert accepts. If the agent changed both a rule and the spec that checked it in one commit, that is the change to read first.

### Is this ready for production?

Chronicle, Arc, Specifications, the CLI and the MCP server are released. See [production readiness](/production-readiness/) for what to check before you depend on them. Review models proposed by Prologue and code generated from Screenplay. Stage's runtime is a disposable sandbox for supported modeled behavior, not a production host; it does not execute every Screenplay construct.
