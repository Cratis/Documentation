To explain how a business record reached its current state, build another view of its history, or find the frontend code affected by a backend change, choose the capability your feature needs first. Cratis Platform products supply those capabilities through event sourcing, generated contracts, and shared models. This reference maps each result to the products involved, their dependencies, and their terms.

## One idea, all the way down

Start with the question your feature must answer. If it needs to explain how it reached its current state, [Chronicle](/chronicle/) keeps the event history and derives read models from it. [Arc](/arc/) supplies the application boundary, separating changes from reads through CQRS. You can [use either independently](/why-cratis/), including Arc over current-state storage without Chronicle.

For a C# backend, Arc's proxy generator produces the [typed TypeScript client](/arc/understanding-the-proxy-boundary/) your frontend calls. [Components](/components/) consumes that contract in React forms, dialogs, and tables. Configure generation in the backend before connecting the screen; you still implement the feature's behavior and check its runtime integration.

Before writing code, an [event model](/event-modeling/) lets you name the commands, events, and views together. [Cratis Screenplay](/screenplay/) keeps that model in a `.play` file, and [Studio](/studio/) provides a collaborative workspace for editing it. The same model can feed [source generation](/cli/reference/screenplay/) for review and further implementation. Check the renderer's supported constructs and languages before choosing that route. For an existing system, [Prologue](/prologue/) offers a separate capture-and-model path.

Add [AuthProxy](/authproxy/) when the application needs authentication, tenant resolution, and routing at the edge. For local .NET hosting, the [Aspire integration](/chronicle/hosting/aspire/) lets your AppHost manage the Chronicle kernel, its separate server process. Once the application is running, use the [CLI](/cli/) and Workbench to inspect events and processing state.

<Aside type="note" title="Modeling tools are optional">
Studio, Screenplay, Stage, Scene, and Prologue support design before implementation. Studio is a paid collaborative workspace built on Chronicle. Arc, Chronicle, and Components do not depend on these modeling tools, so you can build directly in code. Generated output still needs review.
</Aside>

In .NET, the [`Cratis` package](/arc/backend/csharp/chronicle/cratis-package/)'s `AddCratis`/`UseCratis` calls configure and activate Arc and the Chronicle client in the application host. The Chronicle kernel runs separately; the client connects to it over gRPC. Kotlin, Java, and TypeScript backends wire Arc and Chronicle through their own hosts: `io.cratis:cratis` is the single dependency for a Spring Boot application, and [`@cratis/cratis`](/arc/backend/typescript/chronicle/cratis-package/) registers both with one builder call in Node.js (published on npm at 1.0.0). [Arc backends](/arc/backend/) compares the hosts.

To connect Arc and Chronicle, follow the guide for your backend: [Integrate with Chronicle](/arc/backend/csharp/chronicle/) for C#, the [Chronicle guide for Kotlin and Java](/arc/backend/kotlin/guides/chronicle/), or the [Chronicle integration for TypeScript](/arc/backend/typescript/chronicle/). Each explains how a handler's return becomes an event, how the event source id selects its stream, and how a query serves the projected read model.

Follow only the handoffs your application needs. The map below connects modeling to application behavior, identity, event storage, React UI, and operations; each component's guide owns its setup.

## Run a Screenplay as an application sandbox

[Run the Screenplay in Stage](/stage/docker/), send a command, and see the resulting state before implementing the feature. Stage runs the supported subset as a disposable sandbox, not a production host; bind published ports to `127.0.0.1`. To produce application code instead, [render source you own](/cli/reference/screenplay/) for review, customization, and building. Sandbox execution and rendering have separate capability limits; neither supports every model construct or language.

## Run the whole stack from one AppHost

For the Chronicle-backed .NET path shown here, the application connects to a separately running Chronicle kernel. The .NET Aspire resource lets your AppHost manage that kernel alongside the API; it does not move the kernel into the API process. Add the `Cratis.Chronicle.Aspire` package to the AppHost project, then register the resource and pass its reference to the API:

```csharp title="AppHost/Program.cs"
var builder = DistributedApplication.CreateBuilder(args);

var chronicle = builder.AddCratisChronicle();

builder.AddProject<Projects.MyApi>("api")
    .WithReference(chronicle);

builder.Build().Run();
```

With no arguments, `AddCratisChronicle()` registers a resource named `chronicle` running the development
image with embedded MongoDB. When you start the AppHost, it starts that resource alongside the API;
`WithReference(chronicle)` supplies the API's connection string.

<Aside type="caution" title="Development and production use different images">
The development image is for development and CI only.

The optional `AddCratisChronicle` callback configures Chronicle in either mode. Aspire run mode defaults to the development image; for deployment, publish mode defaults to the production image. That image has no embedded database and no development conveniences, so it will not start until you
configure three things: storage (MongoDB, PostgreSQL, SQL Server, or SQLite), a TLS certificate, and an
encryption certificate (unless authentication uses an external authority). Compliance encryption keys can also
live in HashiCorp Vault or Azure Key Vault.
</Aside>

Aspire AppHost is a .NET hosting option, not a backend-language API. TypeScript and JVM backends can
connect to a separately hosted Chronicle kernel; [choose a kernel hosting model](/chronicle/get-started/choose-hosting-model/)
if you aren't using Aspire. [Chronicle's Aspire integration](/chronicle/hosting/aspire/) covers its
images, storage options, ports, and connecting .NET clients.

## Security and compliance end to end

Authentication, authorization, tenancy, and compliance are separate concerns, but they travel through the
same request. AuthProxy authenticates and resolves tenant context. Arc authorizes the command or query.
The Arc + Chronicle integration writes events into the tenant's Chronicle namespace. Chronicle encrypts
personally identifiable information (PII) by compliance subject, and Arc releases protected read models before serving query responses.

[Auth and compliance end to end](/auth-and-compliance/) shows that flow across the stack: where identity
is enriched, where access decisions happen, how subjects differ from event source ids, and what erasure
requires after protected data has reached read models.

## Test the same flow

The same column you draw in an event model is also the shape of the test:

```mermaid
eventmodeling

tf 01 ui  Authors.RegisterAuthorScreen
tf 02 cmd Authors.RegisterAuthor { authorId: uuid, name: string }
tf 03 evt Authors.AuthorRegistered { name: string }
tf 04 rmo Authors.Author ->> 03
tf 05 ui  Authors.AuthorsScreen ->> 04
```

Turn that flow into a behavior-driven specification, with Given describing the starting state, When the action, and Then the result:

| Given | When | Then |
|---|---|---|
| no author exists for this id | `RegisterAuthor` runs through Arc | the command succeeds |
| no author exists for this id | `RegisterAuthor` runs through Arc | Chronicle records `AuthorRegistered` |
| `AuthorRegistered` exists | the read model projection handles it | the `Authors` screen can read the author |

In .NET, Cratis Specifications gives that shape a light wrapper over xUnit: `Establish()` is the given, `Because()` is the when, and each `[Fact]` is one then. Arc adds `CommandScenario<TCommand>` so the command runs through the real pipeline. Chronicle adds in-process scenarios for events, projections, and reactors. Together, you test the slice in the same language you designed it: facts in, command happens, facts and read models out.

Kotlin, Java, and TypeScript backends also run the command through the real Arc pipeline and test the read model in process (Java calls its reducer directly). [Testing with Cratis](/testing-with-cratis/) lists the test packages for each backend and walks through the same slice and its specs in every language.

## Build it with AI

Cratis gives an AI assistant documented conventions for development and tools for inspecting a running Chronicle store. The guidance covers feature shape, naming, generated contracts, Chronicle diagnostics, and the CLI command catalog. You remain responsible for reviewing changes and checking behavior.

For development guidance, install Cratis AI skills into a repository with `cratis ai install`, or add them to one coding tool through its plugin. The rules cover vertical slices, `Handle()` on the command record, and model-bound projections. Projects from the `dotnet new` templates ship a `.cratis/ai.json`, so run `cratis ai update` once; `cratis new` does that for you.

For runtime inspection, `cratis init` writes the CLI's command catalog and assistant instruction files into your project. An agent can then find the commands for browsing events, watching observers, and diagnosing a stuck partition. The Chronicle Model Context Protocol (MCP) server offers a separate connection to a running store for inspecting events, observers, and read models and managing jobs.

[AI-native development](/ai/) covers the setup and available tools. [Agentic development with event sourcing](/agentic-development/) explains how the event log, commands, and specifications give you concrete behavior to check when reviewing an agent-written change.

For a question about the framework, [Prompter](/prompter/) is the community's Discord assistant. It answers from this documentation with citations so you can follow the answer back to its source.

## Direct: govern agentic engineering

To set how far agent work may progress and inspect the evidence behind each next step, use [Cratis Direct](https://cratis.direct/), the control plane for agentic engineering. A person sets the progression ceiling. Journeys define stages of work, gates evaluate recorded evidence, and five loops organize the work: **Deliver, Assure, Operate, Publish, and Steer**. Direct is GitHub-first, lets you bring your own model provider, and is event-sourced on Chronicle. It coordinates agent work; [Cratis AI](/ai/) supplies framework conventions and guidance.

Direct runs Cratis's own engineering today. Access opens in stages to enabled accounts, who [sign in with GitHub](https://app.cratis.direct/); a GitHub account alone does not grant access. Gates depend on the rules you activate, and an LLM assessment is a judgment, not proof. The [public Direct documentation](/direct/) covers the Direct Agent Runner, not a complete service manual.
