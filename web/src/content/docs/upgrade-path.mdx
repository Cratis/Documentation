Before upgrading Cratis Chronicle, find out whether the change affects application code, stored data,
or communication between the server and its clients. A version bump and rebuild may be enough for
one boundary; another may require a stored-state migration. When crossing several majors, you need
the instructions for every boundary between your current and target versions.

Choose those versions below. This planner reads Chronicle's major-version guide; links for the other
Cratis products follow it.

## How to read this

A compile-time boundary changes an API your code uses. Fix the accumulated compile errors against
the version you plan to run, rather than rebuilding your application at each intermediate version.

A stored-state boundary concerns data already written. Follow these instructions in order: skipping
an intermediate release does not skip its data changes. Before crossing one, take a backup, verify
you can restore it, and rehearse the upgrade against a copy.

A wire boundary changes the protocol between the Chronicle kernel (the server) and its clients.
The kernel and .NET client must move together across these boundaries. For example, a 16-to-18
upgrade crosses wire changes at both 16-to-17 and 17-to-18; read both entries before choosing a
client version.

Chronicle verifies compatibility across released minors within one major; crossing a major permits
a protocol change. The TypeScript, Kotlin/Java, and Elixir clients have their own version numbers
and check wire compatibility with the kernel when they connect. Check the pairings in
[Version compatibility](/compatibility/#which-pairings-are-verified), not just matching version numbers.

Each entry links to the full account in Chronicle's own upgrade guide, which is where this
list comes from. Read that entry before changing a deployment; the planner summarizes it rather
than replacing the instructions.
