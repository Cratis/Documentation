Cratis Platform helps teams explain current state from recorded facts, answer new questions from that history, and check which typed frontend usages a backend contract change affects. It is a set of tools for building information systems with event sourcing, Command Query Responsibility Segregation (CQRS), and React interfaces. You can start with one product or connect them in a full-stack application.

## What does your team need to do?

<CardGrid>
  <Card title="Explain how a change happened" icon="seti:db">
    Keep the sequence of business facts behind today's state. [Cratis Chronicle](/chronicle/) stores changes as events with sequence numbers and correlation, identity, and causation context. That explains the facts and context you recorded, not every human reason or a separate read/access audit.
  </Card>
  <Card title="Build a new view from existing history" icon="open-book">
    Answer another question with a focused read model. Chronicle [projections](/chronicle/projections/) derive multiple views from the same events; supported replay rebuilds a view from available history. Projections update asynchronously, and replay cannot recover facts you never recorded.
  </Card>
  <Card title="Find frontend code a contract change affects" icon="puzzle">
    Regenerate the TypeScript clients after a backend change, then type-check the frontend for incompatible typed usages. [Cratis Arc](/arc/) separates changes into commands and reads into queries, and generates those clients. [Cratis Components](/components/) uses the contracts in React. This check does not replace runtime integration checks.
  </Card>
</CardGrid>

## One feature, from facts to a read model

A shopping cart records items added and removed. A caller needs a different answer: what is in this cart now? A projection derives that answer from the events and stores it as a read model, a view of the data shaped for a particular question. The history remains available when you need to explain how the cart reached that state.

Start with the [first-projection C# code walkthrough](/learning-paths/#first-projection). Follow one cart id from recorded facts to a projected cart summary, then see how a checkout fact changes that summary. The example checks the append and waits for processing before reading the cart. This is a console source walkthrough, not an HTTP backend or a running React screen. To run it, follow the sample's setup instructions.

## Extend the feature when you need to

When the feature needs an API and a screen, Arc exposes its commands and queries and generates the TypeScript proxies your React code calls. Components supplies forms, dialogs, and tables that consume them. For a C# backend, changing a contract, regenerating its proxies, and type-checking the frontend reveals incompatible typed usages. That check does not replace runtime integration checks.

[Build a full-stack feature](/build-a-full-app/) follows this handoff from a command to an event, a read model, and a React screen. It is a separate API/UI journey, not a hidden requirement of the cart walkthrough. Once an event-sourced application is running, use the [CLI](/cli/) to inspect events and processing state. [Cratis AI](/ai/) supplies conventions and diagnostics for an assistant; you still review its changes.

To discuss what the feature should do before implementing it, keep its design in [Cratis Screenplay](/screenplay/), a text-based `.play` model of commands, events, views, and specifications. [Cratis Studio](/studio/) lets a team edit that model together. The model can feed [source generation](/cli/reference/screenplay/) as well as implementation by hand, so the design does not have to stop at a diagram. Generated output needs review, and supported constructs and languages depend on the tool you choose.

## Run an event model as an application sandbox

Before implementing a feature, you can [send a command and see its resulting state in Stage](/stage/docker/) from the same Screenplay model. Stage runs the supported subset as a disposable sandbox, not a production host; keep published ports bound to `127.0.0.1`.

## Choose the boundary that fits

You can adopt Chronicle without Arc, use Arc without event sourcing, and leave Components out of the frontend. [Adopting Cratis](/adopting-cratis/) helps choose that boundary; [Why developers choose Cratis](/why-cratis/) discusses the reasons and trade-offs. For a route matched to your work, choose a [learning path](/learning-paths/): new to event sourcing, building a full-stack app, evaluating the platform, operating Chronicle, or joining a frontend team. The [Platform capability map](/cratis-stack/#capability-map) compares product responsibilities and terms.

If you need to erase protected personal values without discarding the event sequence, [event sourcing and GDPR](/concepts/event-sourcing-gdpr/) explains Chronicle's mechanism and the responsibilities it leaves with your application.

<Aside type="note" title="Check product terms and language support before choosing">
Open-source components and hosted products have different terms. Studio is an optional paid workspace; Direct access opens in stages to enabled accounts. Consult the [capability map](/cratis-stack/#capability-map) for product roles and licences and the [support matrix](/compatibility/#support-matrix) for per-component boundaries; the C# example establishes no support or behavior for another language.
</Aside>
