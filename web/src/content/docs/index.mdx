## One feature, from intent to evidence

A librarian asks to register an author in a library. That sounds like a form and a
row in a database, until you need to explain who registered the author, why the
list has not updated, or what an agent changed to make it work.

Cratis Platform connects those questions to the same feature:

1. **Describe the behavior.** Name the intent (`RegisterAuthor`), the fact it
   records (`AuthorRegistered`), and the author list the user needs. An
   [event model](/event-modeling/) makes the handoffs visible before coding.
2. **Build the slice.** [Arc](/arc/) handles the command and generates its
   TypeScript proxy. [Chronicle](/chronicle/) appends the event and projects a
   read model. [Components](/components/) uses the proxy in a React dialog;
   an observable query brings the projected author back to the screen.
3. **Verify and inspect.** [Specifications](/testing-with-cratis/) check the
   behavior. The [CLI](/cli/) and [Workbench](/chronicle/workbench/) let you
   inspect the event and projection when the running result needs explaining.

[Build this feature end to end](/build-a-full-app/). The guide names the files,
backend differences, and checkpoints, so you can follow the same author from
command to event to screen.

## What changes when an agent joins the work?

Without project guidance, an agent has to infer where behavior belongs, invent
an API client, and guess how to investigate a stale screen. You still have to
review all of it.

With Cratis, you give it [the framework's rules and skills](/ai/) before asking
for a change. It works on a bounded slice, leaves generated proxies to the
build, and adds given/when/then specifications. After running the app, you or
the agent can inspect the recorded event and observer state through documented
tools instead of treating a plausible code diff as proof.

The result is a reviewable chain: the requested behavior, the implementation,
the checks, and the runtime facts. Agents can help throughout that chain;
your team still owns the model, permissions, deployment, and acceptance of the
change. [Follow the agentic lifecycle](/ai/#one-feature-through-the-agentic-lifecycle).

## Choose your first boundary

You do not need the whole Platform to get started. Chronicle works without Arc;
Arc works without event sourcing; Components is optional React UI for Arc's
contracts.

## Know what you are adopting

Cratis Platform is a family of products, not one versioned bundle or a promise
that every combination is verified. [The capability map](/cratis-stack/#capability-map)
names the products and their maturity; [version compatibility](/compatibility/)
explains package, client, kernel, and frontend constraints.

- **The application path:** Chronicle, Arc, Components, Fundamentals,
  Specifications, CLI, and Workbench publish packages or images. Released
  does not by itself establish production readiness for your deployment.
- **AI guidance:** Cratis AI is in Preview. Skills help an agent follow the
  framework; they do not certify its output.
- **Model-first tools:** Screenplay, Stage, and Prologue are experimental.
  Studio is a collaborative workspace for event modeling. See the
  [Studio website](https://cratis.studio/) for access and pricing. None is required
  to build the feature above, and generated output needs review.
- **Languages and storage:** Chronicle has a first-class .NET client and
  TypeScript, Kotlin/Java, and Elixir clients. Go is experimental; Python is
  not yet published. Storage choices are MongoDB (default), PostgreSQL,
  Microsoft SQL Server, and SQLite. See the [support matrix](/compatibility/#support-matrix)
  for per-component boundaries, including the Arc TypeScript source preview.
- **Licensing:** The open-source Cratis products are MIT licensed and free
  to use. Studio is paid; paid support and managed operational responsibility
  are separate from running the open-source software yourself.
