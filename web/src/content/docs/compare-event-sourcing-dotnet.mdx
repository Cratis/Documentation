Choosing an event store for a C# application starts with where you want it to run. KurrentDB is a dedicated event database. Marten runs inside your .NET application and stores events and documents in PostgreSQL. Cratis Chronicle is a separate event-sourcing server that also manages event processing.

Use this comparison to decide which boundary fits your application, then check the versions and sources for the capabilities you need. For a two-product view, see [Marten vs Chronicle](/compare/marten-vs-chronicle/) or [KurrentDB vs Chronicle](/compare/kurrentdb-vs-chronicle/). [How Cratis writes comparisons](/compare/) explains the method.

## Comparison layers

An append followed by a read is a useful starting point. With Marten, an inline projection can update a document in the transaction that captures the event. With KurrentDB, the documented approach for many application read models is a separate view fed by a subscription. Chronicle offers reducers and declarative projections to derive typed read models. These choices affect where your application code runs and when a reader sees the change.

The matrix compares those overlapping concerns, not entire product families. The Critter Stack and the wider Cratis ecosystem add adjacent tools; their capabilities are not all features of Marten or Chronicle.

## What is being compared

- **KurrentDB (formerly EventStoreDB)** — a purpose-built event database with official clients for several languages, server-managed persistent subscriptions, projections, and connectors.
- **Marten** — a transactional document database and event store for .NET applications using PostgreSQL, with inline, asynchronous, and live projection models.
- **Cratis Chronicle** — an event-sourcing database and processing runtime with a separate server, multiple storage providers, and released clients for .NET, TypeScript, Kotlin/Java, and Elixir.

Marten is also part of the Critter Stack. [Wolverine](https://wolverinefx.net) is its messaging and web-development framework, with documented transport support, failure policies, and persistent inbox/outbox messaging. Polecat brings the event-store and document-database model to SQL Server, while Fisher targets SQLite. Chronicle belongs to the wider Cratis ecosystem, where [Arc](/arc/), [Components](/components/), the [Cratis CLI](/cli/), and Workbench cover adjacent application and operating concerns. These are separate products in their respective families, not features attributed to Marten or Chronicle itself.

## Where each option fits

Start with the boundary you need your team to own: the application process, the event server, or a wider application framework.

### KurrentDB

KurrentDB fits when you want dedicated event infrastructure and intend to choose the application architecture separately. Its official clients, server-managed persistent subscriptions, and connectors let you consume events across several languages and systems without adopting a CQRS application framework. CQRS separates operations that change state from queries that read it.

### Marten and the Critter Stack

Marten fits when your application is .NET, PostgreSQL is an accepted dependency, and you want events and documents in one database. Its inline projections are useful when a document must be updated in the transaction that captures the event; asynchronous and live projections cover different read needs.

For a wider application model, evaluate the Critter Stack separately. Polecat targets SQL Server, Fisher targets SQLite, and Wolverine provides messaging and web-development features. Those are product choices beyond Marten itself.

### Cratis Chronicle and the Cratis ecosystem

Chronicle fits when you want a separate runtime to manage event storage and processing, with documented storage-provider choices and several language clients using the same server contracts. You take on the operation of that server as well as its storage.

If you also want an application framework, Arc adds commands, queries, and generated TypeScript contracts, while Components supplies React UI components. The CLI and Workbench support inspection and operations. You can evaluate those tools without treating them as requirements that every event store should meet.

## Questions to answer before choosing

1. **Process boundary:** Should event storage and processing run inside the application or behind a separate server?
2. **Database boundary:** Do you want PostgreSQL as the fixed foundation, a purpose-built storage engine, or a runtime with documented provider choices?
3. **Application model:** Do you want to assemble the CQRS and messaging layers yourself, adopt the Critter Stack's .NET model, or use the wider Cratis application path?
4. **Projection model:** Which work must share the append transaction, and which work may run asynchronously or on demand?
5. **Language boundary:** Is .NET the only application boundary, or must several language clients use the same event server?
6. **Operations:** How will your team inspect subscription progress, failed processing, parked work, projections, replay, and recovery for the exact topology you deploy?
7. **Commercial and license boundary:** Which server features, support terms, and licenses apply to the exact products you intend to run?

## Decision criteria to verify separately

This comparison does not score several decision-critical dimensions that depend on the exact deployment profile:

- append and side-effect atomicity, plus read consistency;
- event schema evolution, replay, and migration behavior;
- backup, restore, upgrade, failure, and recovery procedures;
- authentication, tenancy, encryption, PII, and redaction controls; and
- support, commercial terms, and operational responsibility.

Verify each dimension against the exact product versions and deployment profiles before choosing.

## Limitations

This is a documentation comparison, not a benchmark or production evaluation. Client and storage-provider availability do not establish parity. A capability absent from this table may belong to another product in the same family; family membership does not establish integration depth, compatibility, support, or shared commercial terms.
