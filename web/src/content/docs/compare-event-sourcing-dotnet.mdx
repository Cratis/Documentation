Choosing an event store for a C# application starts with where it runs. Marten runs inside your application on PostgreSQL. KurrentDB is a dedicated event database. Cratis Chronicle is a separate event-sourcing server that also manages event processing.

The Cratis team wrote this guide; Chronicle is our product. This selection guide replaces the historical capability matrix. Use the focused [Marten comparison](/compare/marten-vs-chronicle/) and [KurrentDB comparison](/compare/kurrentdb-vs-chronicle/) for versioned details.

## Comparison layers

Consider an order that appends an event, updates a document, and sends a message. Decide which changes must commit together before choosing a projection or messaging API. A server checkpoint does not make a consumer's external side effect part of the append transaction.

## What is being compared

Marten is a .NET document database and event-store library. KurrentDB and Chronicle are servers accessed through SDKs. Wolverine and Arc are optional application tools, not capabilities to attribute to the event stores themselves.

## Core comparison

Marten's [inline projections](https://github.com/JasperFx/marten/tree/V9.62.0/docs/events/projections) can update documents in the event-capture transaction. KurrentDB's [projections](https://docs.kurrent.io/server/v26.2/features/projections/intro.html) emit or link events; consumers can build external application views. Chronicle's [kernel projections and application-side reducers](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/architecture.mdx) build read models across a server boundary. Choose according to the consistency your reader needs.

## Where each option fits

### KurrentDB

Choose KurrentDB when you want its stream database and [subscription model](https://docs.kurrent.io/server/v26.2/features/persistent-subscriptions.html), while choosing the application's command handlers and read-model consumers separately. Evaluate its [connectors](https://docs.kurrent.io/server/v26.2/features/connectors/intro.html) for downstream integration. In 26.2, multi-node deployments require a license; single-node deployments no longer need a key for previously enterprise features ([installation](https://docs.kurrent.io/server/v26.2/quick-start/installation.html)).

### Marten and the Critter Stack

Choose Marten when PostgreSQL and .NET fit your application and events and documents need a shared transaction. Optional [Wolverine 6.64.2 integration](https://github.com/JasperFx/wolverine/blob/V6.64.2/docs/guide/durability/marten/transactional-middleware.md) can include outgoing messages in the Marten transaction through its transactional outbox. It requires configured integration and transactional handling; sharing a product family alone does not create that guarantee.

### Cratis Chronicle and the Cratis ecosystem

Choose Chronicle when you want a separate runtime to coordinate storage and processing. You operate the kernel and its [storage](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/hosting/configuration/storage.mdx). [Clustering](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/hosting/configuration/clustering.md) supports MongoDB or SQL with PostgreSQL or SQL Server; SQLite and in-memory storage are not multi-node choices. [Arc](/arc/) is a separate application-framework choice.

## Questions to answer before choosing

- Must the append, document update, and outgoing message share a transaction?
- Which process owns retries, checkpoints, and duplicate handling?
- Can your team operate an event server as well as its storage?
- Which operations must your chosen language client expose?

## Decision criteria to verify separately

Try one application feature with the intended topology. Include conflicting writes, a consumer restart, replay, and recovery from a failed side effect. Review backup, restore, authentication, personal-data handling, and commercial terms for those exact versions.

## Limitations

This guide is not a benchmark or production evaluation. Storage-provider availability and language-client availability do not establish parity.
