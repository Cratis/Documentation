You run Cratis applications on your own infrastructure. You need to decide how users sign in, how invitations reach people, and how tools such as MCP clients authenticate.

There are three profiles. All of them put [AuthProxy](/authproxy/) at the edge, and we recommend configuring signed forwarded identity between AuthProxy and Arc in every one of them. The profiles differ in where tokens come from.

:::note[Available and planned]
Some components ship today and others are planned. The tables below say which. Planned items are direction, not a delivery commitment; see the [roadmap](/roadmap/). This page is updated as each profile ships.
:::

## Choose a profile

| Profile | Who it fits | What signs people in | What API and MCP clients use |
| --- | --- | --- | --- |
| Minimal | Small teams that do not want to run an authorization server. | AuthProxy, against the provider you configure. | Personal access tokens (**Planned**), validated inside your install with no call to Cratis cloud. |
| Bring your own IdP | Organizations with an existing identity provider, for example Microsoft Entra ID or Okta. | AuthProxy, against your OpenID Connect provider. | Access tokens from your authorization server, accepted on bearer routes. Personal access tokens alongside them are **Planned**. |
| Full | Operators who want the Cratis consent screen, `cratis` CLI sign-in, and remote MCP connectors. | A Cratis Identity realm that you operate yourself (**Planned**). | Tokens issued by that realm (**Planned**). |

## Sign forwarded identity in every profile

AuthProxy authenticates the caller and forwards identity to Arc. AuthProxy can sign that forwarded identity and Arc can verify it. Signing is opt-in: when both sides are configured, Arc accepts forwarded identity only when its signature verifies.

Signing needs AuthProxy 2.44.0 or later and Arc 22.168.0 or later. See [forwarded identity signing](/authproxy/configuration/forwarded-identity-signing/) in AuthProxy and [signed forwarded identity](/arc/backend/csharp/asp-net-core/signed-forwarded-identity/) in Arc. If you run AuthProxy under Aspire, the [Aspire guide](/authproxy/aspire/#signed-forwarded-identity) covers the pairing.

:::tip
Turn on signed forwarding for every service in every profile. Signing as the default, with unsigned identity accepted only in local development, is **planned**.
:::

## Invitations without mail

Ante signs invitation links and runs the lobby. It never sends email. Your application receives the link and decides how to deliver it: through your own mail service, or by showing it to an administrator to copy and send.

AuthProxy validates the link and runs sign-in. See the [lobby](/authproxy/configuration/lobby/) documentation and the [Ante repository](https://github.com/Cratis/Ante). Both are available today.

If you run no onboarding service, your application adds members through its own authenticated administration path. If you run no MCP clients, the browser application works unchanged.

## Disconnected does not mean one process

A disconnected install makes no call to Cratis cloud. It still runs AuthProxy, Ante if you use it, and, in the full profile, an identity host as separate containers on your own network.

Packing those components into one process, or embedding identity in your application's host, would be a different, optional compact deployment. That is not what disconnected means, and it is not offered as a profile.

In the minimal profile, personal access token validation is planned to happen locally, with no outbound call (**Planned**). Browser sign-in still talks to the OIDC provider you configure.
