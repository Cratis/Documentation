For TypeScript and Node.js event sourcing, choose where event processing should run. Emmett puts the framework in your application. The KurrentDB Node client connects to a separate event database. Cratis Chronicle also runs as a separate server, but manages read models (views derived from events) and tracks consumer progress alongside the log.

This choice affects the next feature you build. With Emmett, you compose handling and projections around a storage adapter. With KurrentDB's client, you choose the application layer and consumers around the database. With Chronicle, a projection maps events to a view in the server; a reducer computes state in your application while the server tracks progress. Check the client guide for the APIs available in TypeScript.

Arc.TypeScript is a separate, optional choice for the application's command and query layer. This separation is Command Query Responsibility Segregation (CQRS): commands change state, while queries read it. Arc.TypeScript is published on npm at 1.0.0, and Chronicle does not require it. None of these options removes the need to design concurrency checks or handle failures.

The comparison snapshot is dated 2026-10-20. The versions below establish its scope; they are not recommendations to install the latest release. Check publication and compatibility for the versions you intend to use.

| Arc.TypeScript | npm release 1.0.0 ([`@cratis/arc.core`](https://registry.npmjs.org/@cratis/arc.core)) | Published on npm at 1.0.0, installable with `npm install @cratis/arc.core`. | KurrentDB Node client | [`@kurrent/kurrentdb-client` 1.3.1](https://www.npmjs.com/package/@kurrent/kurrentdb-client/v/1.3.1), published 2026-06-29 | gRPC client for a separately deployed KurrentDB server, not a CQRS application framework. |

This comparison uses the KurrentDB client rather than the older EventStoreDB package name. Its [versioned package README](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/blob/v1.3.1/packages/db-client/README.md) describes KurrentDB 20+ and says tests run exclusively against long-term-support (LTS) server versions. Select a supported server/client pairing; a client version is not a server version.

The [npm registry metadata for Chronicle](https://registry.npmjs.org/@cratis/chronicle), [Emmett](https://registry.npmjs.org/@event-driven-io/emmett), and [KurrentDB's client](https://registry.npmjs.org/@kurrent/kurrentdb-client) supplies publication dates. Arc's [README](https://github.com/Cratis/Arc.TypeScript/blob/main/README.md) describes its parity boundaries. Recheck those sources before adoption or an upgrade.

## What runs where

| Dimension | Chronicle with optional Arc.TypeScript | Emmett | KurrentDB Node client |
|---|---|---|---|
| Storage and ownership | Your Node.js application uses the Chronicle client over gRPC, a remote procedure call protocol. The separate kernel stores events and manages processing. Arc.TypeScript hosts application commands and queries; it is not the database. | The framework runs in your Node.js process. Its [documented adapters](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#features) include PostgreSQL, EventStoreDB, MongoDB, SQLite, and in-memory storage. You choose the backing store and its deployment. | Your Node.js application uses the client over gRPC to KurrentDB. The database is a separate operational component; the client does not embed it. |
| Writes and concurrency | Typed event registration and append APIs in the client; use the documented [TypeScript event-sourcing flow](/event-sourcing/typescript/) and explicit append outcomes. | Command-handling patterns and store implementations are part of the framework. Read the selected adapter's contract for transaction and concurrency behavior. | The [TypeScript example](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/blob/v1.3.1/packages/db-client/README.md#example) shows typed JSON events, append, and stream reads. Application command handling is your responsibility. |
| Projections and read models | Chronicle runs declarative projections in the kernel and materializes read models. Reducer handlers run in the connected application while the kernel tracks progress. The TypeScript client exposes projection registration, reads and watches; see [client capabilities](/chronicle/clients/typescript/). | Emmett includes projections for building read models from events. Their storage and execution depend on your chosen adapter and application setup, rather than a mandatory Emmett server. | Client subscriptions and KurrentDB server projections are distinct tools. Choose how consumers build application read models and own their lifecycle; see the [server comparison](/compare/kurrentdb-vs-chronicle/). |
| CQRS application layer | Arc.TypeScript supplies commands, queries, validation, hosting adapters, and bounded generated clients. It is [published on npm with explicit gaps](/arc/backend/typescript/), not full Arc on .NET parity. Chronicle can be used without Arc. | Command patterns, Express integration, and testing utilities are documented framework features. You compose the HTTP boundary and read-model access for your application. | The SDK is a database client. Pair it with your chosen command/query framework, HTTP host, validation, and UI integration. |
| Deployment and operations | Operate the Chronicle kernel and its storage as well as the Node.js app. Arc.TypeScript does not remove that server boundary. Follow the [compatibility matrix](/compatibility/). | Deploy the Node.js app plus the backing store you select. SQLite or in-memory development has a different operational footprint from PostgreSQL or a dedicated event database. | Operate KurrentDB, or select a hosted offering, plus your Node.js application and consumers. Follow the client's LTS compatibility policy. |
| Testing | Chronicle's client has [fixture-backed scenarios](https://github.com/Cratis/Chronicle.TypeScript/blob/v6.53.1/Documentation/testing.md); Arc.TypeScript has test helpers (`@cratis/arc.testing`) with documented coverage limits. Test against the deployed kernel contract as well as application units. | Built-in unit, integration, and BDD-style testing utilities and Testcontainers support are [documented features](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#features). | The repository provides [client samples and tests](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/tree/v1.3.1/packages/test/src/samples). Design application-level tests for your chosen CQRS and read-model implementation. |

Emmett's feature descriptions come from its [0.42.4 README](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md). Read its [production-readiness FAQ](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#is-it-production-ready) as the maintainer's assessment, not a comparative reliability measurement. Its [licensing FAQ](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#why-theres-no-license) describes an unresolved licensing direction at this version. Review the terms for the version you choose with your team; do not assume an MIT grant.

## When an alternative is the better fit

Emmett fits an existing Node.js service when you want event handling and projections to remain part of that service. You can choose among its storage adapters without adopting Chronicle's kernel. Read the selected adapter's concurrency and transaction contract, as well as the license terms, before committing to it.

KurrentDB's Node client fits when you already operate KurrentDB or want its stream and subscription model without adopting another application framework. You choose the HTTP host, command handlers and read-model consumers. Those choices give you control, but leave their implementation and deployment with you; the client alone is not the whole KurrentDB ecosystem.

Evaluate Chronicle when you want the server to coordinate projections and event consumers and are prepared to operate its kernel and storage. Start with the released TypeScript client. Add Arc.TypeScript only if its documented capabilities suit your application. Its proxy generator does not establish full parity with Arc on .NET, and the Chronicle integration remains experimental.

If an npm-published Node.js backend framework is a requirement, choose another application layer even if Chronicle remains your event database. [CQRS in TypeScript](/cqrs/typescript/) explains that boundary and the source-based Arc setup.

## A useful evaluation slice

Use a feature whose result you can inspect, such as registering a book and seeing it appear in a catalog. Implement the command with a concurrency expectation, the catalog read model and a live consumer. Then try a duplicate command and a conflicting append. Restart the consumer and rebuild the catalog from history to see who owns recovery and replay.

Run this slice on the storage adapter and server versions you intend to deploy. Record which behavior comes from the database, which comes from the library and which you wrote yourself. This comparison does not establish throughput, reliability or feature parity for that combination.
