For TypeScript and Node.js event sourcing, choose where event processing should run. Emmett puts the framework in your application. The KurrentDB Node client connects to a separate event database. Cratis Chronicle also runs as a separate server, coordinating read-model production and consumer progress.

Arc.TypeScript is an optional command and query layer for the application; Chronicle does not require it. The Cratis team wrote this page, and Chronicle and Arc are our products. See [our comparison method](/compare/).

## What runs where

| Responsibility | Chronicle with optional Arc.TypeScript | Emmett | KurrentDB Node client |
| --- | --- | --- | --- |
| Event storage | A separate kernel reached over gRPC ([architecture](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/architecture.mdx)); Arc is not the database | Framework in the Node.js process with PostgreSQL, EventStoreDB, MongoDB, SQLite, or in-memory adapters ([README](https://github.com/event-driven-io/emmett/blob/0.42.5/README.md)) | Separate KurrentDB server reached through the [Node SDK](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/tree/v1.3.2) |
| Read models | Kernel projections and application reducer handlers; TypeScript has registration, reads, and [watchers](https://github.com/Cratis/Chronicle.TypeScript/blob/v6.67.7/Source/readModels/IReadModelWatcher.ts) | Framework projections with adapter/application-owned execution and storage ([README](https://github.com/event-driven-io/emmett/blob/0.42.5/README.md)) | Client subscriptions are separate from [server projections](https://docs.kurrent.io/server/v26.2/features/projections/intro.html); consumers or [connectors](https://docs.kurrent.io/server/v26.2/features/connectors/intro.html) can maintain external views |
| Application layer | Optional Arc supplies model-bound commands, queries, HTTP adapters, and proxy generation ([capabilities](https://github.com/Cratis/Arc.TypeScript/blob/v1.0.2/Documentation/reference/capabilities.md)) | Command-handling patterns, Express integration, and testing tools ([README](https://github.com/event-driven-io/emmett/blob/0.42.5/README.md)) | Choose the command, query, validation, and HTTP layer around the database SDK |

These choices have different failure boundaries. A Chronicle read-model watcher reconnects, but it does **not** replay changes missed during an outage; refresh the query after reconnect ([watcher contract](https://github.com/Cratis/Chronicle.TypeScript/blob/v6.67.7/Source/readModels/IReadModelWatcher.ts)). With Emmett, transaction and concurrency guarantees depend on the selected adapter. KurrentDB [persistent subscriptions](https://docs.kurrent.io/server/v26.2/features/persistent-subscriptions.html) deliver at least once without guaranteed ordering, so consumers must handle duplicates.

Arc.TypeScript 1.0.2 documents Express 5, Fastify 5, and Hono 4 adapters and bounded Chronicle integration. Its [capability reference](https://github.com/Cratis/Arc.TypeScript/blob/v1.0.2/Documentation/reference/capabilities.md) distinguishes those paths from full .NET parity. Choose it for the documented application features, not as a requirement for Chronicle access.

## When an alternative is the better fit

Emmett fits a Node.js application that wants command and projection patterns in-process and a choice of storage adapter. Its [README](https://github.com/event-driven-io/emmett/blob/0.42.5/README.md) documents unit, integration, and end-to-end testing with BDD syntax and Testcontainers. Evaluate the adapter's durability and concurrency contract independently; in-memory and PostgreSQL deployments are not equivalent.

KurrentDB fits an application that wants a stream database while retaining its own application framework and read-model consumers. Compare [server processing, connectors, and hosting](/compare/kurrentdb-vs-chronicle/) before choosing the client.

Chronicle fits an application that wants kernel-managed processing and read models. You operate the Node.js application, kernel, and selected storage. Optional Arc integration does not remove those components.

## A useful evaluation slice

Implement one command with a conflicting-write case, one read model, and one failed side effect. Restart the consumer and verify the result after replay or reconnection. Run this against the actual backing service as well as any fixtures.

Chronicle's [TypeScript testing fixtures](https://github.com/Cratis/Chronicle.TypeScript/blob/v6.67.7/Documentation/testing.md) do not start a kernel and cover a selected contract subset. Arc's [Chronicle scenarios](https://github.com/Cratis/Arc.TypeScript/blob/v1.0.2/Documentation/reference/capabilities.md) use seeded, keyed models: they do not enforce concurrency or update reduced state after appends. Unsupported list, observation, and aggregate-replay paths need kernel-backed scenarios. A passing fixture test therefore does not prove the deployed processing contract.
