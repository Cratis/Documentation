For a TypeScript or Node.js event-sourcing application, start by choosing **who owns storage and processing**, not by choosing a client API. Emmett is an application framework with several storage adapters. The KurrentDB Node client connects your application to a dedicated event database. Chronicle also runs as a separate database and processing runtime; Arc.TypeScript adds an optional CQRS application layer, but remains a source preview.

**Choose Emmett** when you want application-owned event handling and projections with a choice of stores. **Choose KurrentDB's Node client** when KurrentDB is your event database and you want to own the surrounding application architecture. **Consider Chronicle** when you want the runtime to own event processing and projected state, and evaluate Arc.TypeScript separately against its preview limits.

This is an architectural comparison, not a throughput benchmark or a production-readiness certification. The options operate at different layers, and none removes the need to model events, concurrency, failures, and read models.

## What runs where

| Dimension | Chronicle with optional Arc.TypeScript | Emmett | KurrentDB Node client |
|---|---|---|---|
| Storage and ownership | Your Node.js application uses the Chronicle client over gRPC. The separate kernel stores events and owns processing. Arc.TypeScript hosts application commands and queries; it is not the database. | The framework runs in your Node.js process. Its [documented adapters](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#features) include PostgreSQL, EventStoreDB, MongoDB, SQLite, and in-memory storage. You choose the backing store and its deployment. | Your Node.js application uses the client over gRPC to KurrentDB. The database is a separate operational component; the client does not embed it. |
| Writes and concurrency | Typed event registration and append APIs in the client; use the documented [TypeScript event-sourcing flow](/event-sourcing/typescript/) and explicit append outcomes. | Command-handling patterns and store implementations are part of the framework. Read the selected adapter's contract for transaction and concurrency behavior. | The [TypeScript example](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/blob/v1.3.1/packages/db-client/README.md#example) shows typed JSON events, append, and stream reads. Application command handling is your responsibility. |
| Projections and read models | Chronicle runs declarative projections in the kernel and materializes read models. The TypeScript client exposes registered projections, reads, and watches; see [client capabilities](/chronicle/clients/typescript/). | Emmett includes projections for building read models from events. Their storage and execution depend on your chosen adapter and application setup, rather than a mandatory Emmett server. | Client subscriptions and KurrentDB server projections are distinct tools. Choose how consumers build application read models and own their lifecycle; see the [server comparison](/compare/kurrentdb-vs-chronicle/). |
| CQRS application layer | Arc.TypeScript supplies commands, queries, validation, hosting adapters, and bounded generated clients. It remains a [source preview with explicit gaps](/arc/backend/typescript/), not full Arc on .NET parity. Chronicle can be used without Arc. | Command patterns, Express integration, and testing utilities are documented framework features. You compose the HTTP boundary and read-model access for your application. | The SDK is a database client. Pair it with your chosen command/query framework, HTTP host, validation, and UI integration. |
| Deployment and operations | Operate the Chronicle kernel and its storage as well as the Node.js app. Arc.TypeScript does not remove that server boundary. Follow the [compatibility matrix](/compatibility/). | Deploy the Node.js app plus the backing store you select. SQLite or in-memory development has a different operational footprint from PostgreSQL or a dedicated event database. | Operate KurrentDB, or select a hosted offering, plus your Node.js application and consumers. Follow the client's LTS compatibility policy. |
| Testing | Chronicle's client has [fixture-backed scenarios](https://github.com/Cratis/Chronicle.TypeScript/blob/v6.53.1/Documentation/testing.md); Arc.TypeScript has source-preview test helpers with documented coverage limits. Test against the deployed kernel contract as well as application units. | Built-in unit, integration, and BDD-style testing utilities and Testcontainers support are [documented features](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#features). | The repository provides [client samples and tests](https://github.com/kurrent-io/KurrentDB-Client-NodeJS/tree/v1.3.1/packages/test/src/samples). Design application-level tests for your chosen CQRS and read-model implementation. |

Emmett's feature descriptions above come from its [0.42.4 README](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md). In particular, its [production-readiness FAQ](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#is-it-production-ready) says users already run it in their systems. That is the maintainer's statement, not a comparative reliability measurement. Its [licensing FAQ](https://github.com/event-driven-io/emmett/blob/0.42.4/README.md#why-theres-no-license) also describes an unresolved licensing direction at this version; review the current terms with your team rather than assuming an MIT grant.

## When an alternative is the better fit

**Emmett is a better fit when** you want to compose event sourcing inside an existing Node.js service, choose among its storage adapters, and keep projection/application processing in that service. It offers a path that does not require adopting Chronicle's kernel. Verify the adapter-specific guarantees and licensing for the version you will use.

**KurrentDB's Node client is a better fit when** your organization already operates KurrentDB, wants its stream/subscription model, or wants the event database without adopting another application framework. You retain control over HTTP hosting, command handling, read-model consumers, and their deployment. That control comes with implementation and operational responsibilities; it is not evidence that those features are missing from the KurrentDB ecosystem.

**Chronicle is worth evaluating when** server-owned projections and event processing match your architecture and you are prepared to operate its kernel. Use the released TypeScript client first. If Arc.TypeScript is also attractive, evaluate its source preview independently: source-tag availability does not make `npm install @cratis/arc.core` work, and bounded proxy generation is not full .NET parity.

If a published, stable Node.js backend framework is a requirement today, Arc.TypeScript's source-preview status is a reason to choose another application layer, even if Chronicle remains your event database. See [CQRS in TypeScript](/cqrs/typescript/) for that distinction and the currently supported setup.

## A useful evaluation slice

Implement one command that appends an event with a concurrency expectation, one read model, and one live consumer. Then test a duplicate command, a conflicting append, a consumer restart, and rebuilding the read model from history. Record which guarantees come from the database, which come from the library, and which you implemented yourself. Run that slice on the storage adapter and server versions you intend to deploy; this page makes no benchmark or feature-parity claim for the result.
