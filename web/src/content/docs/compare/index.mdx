Choose an event-sourcing tool by the work your application needs and the services your team can operate. These comparisons explain where Cratis Chronicle and the alternatives fit, from an in-process library to a separate event-store server. Start with your application language or the two products you are deciding between.

The Cratis team writes these pages, and Chronicle is our product. Each comparison names the versions it covers and links to first-party sources so you can weigh the trade-offs yourself.

## How we write them

First, check what runs where. An in-process library executes in your application; a separate event-store server adds a service to operate. A server that also manages event processing takes on responsibility for tracking consumers and building derived views. The tables explain who owns each concern, and the pages identify situations where an alternative fits better.

Read each table as a snapshot of its named versions and review date. A link to unversioned documentation may describe newer behavior. Before choosing, check the versions you intend to deploy and the client APIs your application needs. A shared protocol does not mean equal client coverage, and source in a repository does not establish that a package is published.

Claims about another product link to its own documentation, repository, license or package registry. Chronicle claims use its documentation and README. "Not publicly documented" means we did not find a documented capability in those sources; it does not establish that the capability is absent.

A documented capability is not evidence of throughput, latency or production suitability. We do not score or rank products. Use the comparison to narrow your options, then try one feature from your own domain on the storage and server versions you plan to run.
