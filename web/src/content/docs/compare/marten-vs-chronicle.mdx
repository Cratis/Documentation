If an event append and a document update must share one PostgreSQL transaction, Marten's in-process .NET model fits that requirement. Cratis Chronicle puts storage and processing behind a separate server. The choice changes what can commit together and what you deploy.

The Cratis team wrote this page; Chronicle is our product. See the [.NET selection guide](/compare-event-sourcing-dotnet/) for a third option, KurrentDB, and [our comparison method](/compare/) for scope.

## Choose Marten or Chronicle

Choose Marten when .NET and PostgreSQL fit your application and events and documents need a shared transaction. Its concrete Wolverine integration also matters when outgoing messages must participate in that transaction.

Choose Chronicle when you want a separately deployed runtime to coordinate event storage and processing, or need its storage-provider choices. You take on the kernel and its storage as operational components. Neither choice makes arbitrary external side effects atomic with an append.

## Architecture: library or server

[Marten](https://github.com/JasperFx/marten/blob/V9.62.0/src/Marten/Marten.csproj) runs in your .NET application and uses PostgreSQL for events and documents. Inline projections can update documents in the event-capture transaction. Its [async daemon subscriptions](https://github.com/JasperFx/marten/blob/V9.62.0/docs/events/subscriptions.md) run application processing after capture.

The [Chronicle Kernel](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/architecture.mdx) is a separate server. Applications call it over gRPC. Projections run in the kernel; reducer and reactor handlers run in your application, with the kernel coordinating observation. An append is outside your application's database transaction.

## Projections and read models

Suppose an order event must update an order document before the command returns. Marten's inline projection can make both changes in the PostgreSQL transaction. An async projection instead lets the view catch up, while a live projection derives state on demand ([projection documentation](https://github.com/JasperFx/marten/tree/V9.62.0/docs/events/projections)).

With Chronicle, the append crosses a server boundary. A materialized model can lag behind it; a passive projection computes on read. Kernel projections and application reducers also place computation in different processes. Choose the read contract deliberately rather than treating every projection API as an inline transaction.

## Storage and hosting

Marten's PostgreSQL dependency is part of its design, not a configurable choice of event-store provider. Chronicle's [storage providers](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/hosting/configuration/storage.mdx) and [clustering](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/hosting/configuration/clustering.md) are separate choices: multi-node deployments can use MongoDB or SQL clustering with PostgreSQL or SQL Server. SQLite and in-memory storage are single-node choices; in-memory data is ephemeral.

For tenancy, review Marten's [conjoined and sharded models](https://github.com/JasperFx/marten/blob/V9.62.0/docs/events/multitenancy.md) against your isolation requirements. Chronicle uses namespaces within an event store; namespace routing by itself is not proof of authorization or physical isolation.

## Languages and clients

Marten's library APIs are .NET APIs. Chronicle has independently released clients: [.NET/server 19.181.2](https://github.com/Cratis/Chronicle/releases/tag/v19.181.2), [TypeScript 6.67.7](https://github.com/Cratis/Chronicle.TypeScript/releases/tag/v6.67.7), [JVM 7.13.0](https://github.com/Cratis/Chronicle.Kotlin/releases/tag/v7.13.0), and [Elixir 3.25.0](https://github.com/Cratis/Chronicle.Elixir/releases/tag/v3.25.0). Those releases establish availability, not equal API coverage or a tested pairing. Check [client coverage](/chronicle-clients/) for your operations.

## Operations, observability and AI tooling

For Marten, account for application-hosted daemon processing as well as PostgreSQL. For Chronicle, account for the kernel, storage, and connected handlers. During evaluation, inspect processing position, force a failure, and recover it. Optional administrative or AI tools do not establish that recovery works for your deployment.

## Compliance and personal data

Marten's [event-data masking](https://github.com/JasperFx/marten/blob/V9.62.0/docs/events/protection.md) rewrites selected event members or custom headers when the masking operation runs. Chronicle's [personal-data protection](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/compliance/index.md) encrypts marked properties using a key per subject; deleting that key makes those encrypted values unreadable.

Plan separately for plaintext copies, read models, exports, and backups. Rewriting stored members or deleting a key does not by itself erase every copy or establish regulatory compliance.

## Where Marten is the better choice

Marten avoids a separate event-server deployment and fits applications that need documents alongside events in PostgreSQL. If you also use Wolverine, its [Marten transactional middleware](https://github.com/JasperFx/wolverine/blob/V6.64.2/docs/guide/durability/marten/transactional-middleware.md) can commit event/document changes and outgoing messages to a transactional outbox together.

That guarantee needs [configured integration](https://github.com/JasperFx/wolverine/blob/V6.64.2/docs/guide/durability/marten/index.md) and a supported transactional handling path. Merely injecting a session does not create the commit. The outbox records messages in the transaction; delivery to an external recipient happens afterward.

## Moving between them

A migration changes application code as well as data. Map event identities and schemas, concurrency checks, projection timing, consumer checkpoints, and recovery procedures. Prove the migration on a representative history before switching writers.

## Questions to answer before choosing

- Must event, document, and outgoing-message records commit together?
- Is a separate kernel acceptable to the operations team?
- Which languages need access to the history?
- How much read-model lag can the application tolerate?
- How will erasure reach derived copies and backups?

## Limitations

This is a documentation comparison, not a benchmark or production evaluation. Client and storage-provider availability do not establish parity. The optional ecosystem products have their own integration contracts and terms.
