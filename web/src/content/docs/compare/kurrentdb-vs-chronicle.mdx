KurrentDB and Cratis Chronicle both store events in a separate server. Choose between them by how you want to build read models (views derived from events), connect consumers and operate storage: KurrentDB has its own storage engine; Chronicle uses a storage database you choose and manages event processing alongside the log.

The Cratis team wrote this page, and Chronicle is a Cratis product. KurrentDB was formerly called EventStoreDB. The comparison below covers named versions, with sources beside the capabilities that affect the choice. For a three-way comparison that includes Marten, see [Event sourcing in .NET](/compare-event-sourcing-dotnet/), and for the JVM see [Event sourcing on the JVM](/compare-event-sourcing-jvm/). All our comparisons follow the method in [How Cratis writes comparisons](/compare/).

## Choose KurrentDB or Chronicle

Choose KurrentDB when you want a dedicated event database and plan to build application read models through consumers or connectors. Its documented connectors and Kurrent Cloud service matter if you want ready-made destinations or do not want to operate the database yourself.

Choose Chronicle when you want the server to manage read-model building as well as the event log. A projection maps events into a read model inside the kernel; a reducer computes state in your application while the server tracks progress. Check the APIs in your chosen client before designing around either approach.

Storage choice can settle the decision. Chronicle supports MongoDB, PostgreSQL, SQL Server and SQLite, but the compared version requires MongoDB for multiple nodes. The storage and clustering sections below explain that boundary.

## Architecture: two servers

Both products run as a server that your applications call over the network. Neither runs inside your application process.

KurrentDB is a database that stores events in streams in its own storage engine. Clients talk to it over gRPC, and it also has an HTTP interface ([introduction](https://docs.kurrent.io/server/v26.2/quick-start/)). It runs as a single node or as a cluster of three nodes ([installation](https://docs.kurrent.io/server/v26.2/quick-start/installation.html)).

Chronicle runs as the Chronicle Kernel, built on [Microsoft Orleans](https://learn.microsoft.com/dotnet/orleans/). Clients call it over gRPC, a remote procedure call protocol, and it also exposes HTTP surfaces ([architecture](/chronicle/architecture/)). It stores events in a database you choose and manages the observers that process them. Projections run in the kernel; reducer and reactor handlers run in your connected application, with the server tracking each observer's position.

That changes the work around a new view. With KurrentDB, decide where a consumer writes the view and how it resumes processing. With Chronicle, choose a projection or reducer and the sink where Chronicle writes the result. A sink is the destination database for a read model. Both designs still require you to model the events and handle failures in application side effects.

Its documentation says the source code is available to view and that KLv1 is not an open-source license approved by the Open Source Initiative (OSI) ([introduction](https://docs.kurrent.io/server/v26.2/quick-start/)). The terms changed in 26.2. From that release, single-node deployments have access to all licensed features without a key, and multi-node deployments need a valid license key on every node ([what's new in 26.2](https://docs.kurrent.io/server/v26.2/quick-start/whatsnew.html)). If you plan to run a cluster, read the current terms first.

## Consuming events and building read models

KurrentDB gives you three ways to react to events. Catch-up subscriptions are driven by the client, which stores its own position. Persistent subscriptions keep the position on the server and let several consumers in a group share the load, with at-least-once delivery. Its docs warn that events in a consumer group can arrive out of order ([persistent subscriptions](https://docs.kurrent.io/server/v26.2/features/persistent-subscriptions.html)). Connectors run on the server and send events to external systems through sinks ([Understanding Connectors](https://docs.kurrent.io/server/v26.2/features/connectors/)).

KurrentDB projections are JavaScript that reads events and appends or links new events. Its own docs point out that many problems fit better as a read model in another database populated by a catch-up subscription ([projections](https://docs.kurrent.io/server/v26.2/features/projections/)).

Chronicle maintains a read model from a projection or reducer and writes it to MongoDB or SQL. Materialized read models are eventually consistent: a successful append does not mean the view has caught up. A passive model is computed on read instead, but freshness alone does not protect a command's decision from a concurrent append ([projections](/chronicle/projections/)). Reactors run application side effects; your application remains responsible for making those effects safe to repeat ([observers](/chronicle/concepts/observers/)).

## Storage and hosting

KurrentDB documents [archiving](https://docs.kurrent.io/server/v26.2/features/archiving.html) of older data to cheaper blob storage, [backup](https://docs.kurrent.io/server/v26.2/operations/backup.html) and [scavenging](https://docs.kurrent.io/server/v26.2/operations/scavenge.html) to reclaim space.

Chronicle stores events in a database you choose and ships as the `cratis/chronicle` Docker image, with [production hosting](/chronicle/hosting/production/) and [clustering](/chronicle/hosting/configuration/clustering/) covered in its docs. Choosing Chronicle means running the server in addition to its database. In 19.92.2, multi-node clustering requires MongoDB; PostgreSQL, SQL Server and SQLite support one node. Later versions have different clustering options, so use the hosting documentation for the version you intend to deploy.

## Languages and clients

KurrentDB's introduction lists gRPC clients for Python, Node.js (JavaScript and TypeScript), Java, .NET, Go and Rust, and community clients for Ruby and Elixir ([introduction](https://docs.kurrent.io/server/v26.2/quick-start/)).

Chronicle has a .NET SDK, and released clients for TypeScript (`@cratis/chronicle`), Kotlin and Java (`io.cratis:chronicle`) and Elixir (`cratis_chronicle`). See [Chronicle in your language](/chronicle-clients/) for package availability, including languages outside this snapshot. A client release has its own API surface and version constraints; it does not establish parity with .NET. Check [where the clients differ](/chronicle/clients/where-the-clients-differ/) before depending on a particular operation.

## Compliance and personal data

KurrentDB documents that events are immutable. To remove data, it recommends rewriting the stream to a new stream without the data, deleting the old stream and running a scavenge. If that is impractical, a redaction tool blanks the data of specific events. The docs call it a last resort that may affect subscriptions and projections, and say the tool is available on request ([redaction](https://docs.kurrent.io/server/v26.2/operations/redaction.html)).

Chronicle marks personal data with PII attributes, encrypts those values at rest with a key per subject, and erases a subject by revoking the key. Whole events can be redacted while the sequence and audit metadata remain. See [Chronicle compliance](/chronicle/compliance/) and [Auth and compliance](/auth-and-compliance/).

The design decision comes before the erasure request. Chronicle can erase access to values that were marked and encrypted when appended; key deletion does not reach plaintext copies held elsewhere. KurrentDB's documented approaches rewrite or blank stored events, or move data to a new stream. Neither mechanism alone establishes that your application meets its regulatory obligations.

## Where KurrentDB is the better choice

KurrentDB fits when you want to keep the event database separate from your application framework and choose how consumers build views. Its official Python, Go and Rust clients may also settle a language requirement. Compare the operations you need with Chronicle's [client coverage](/chronicle-clients/), rather than treating a language name as a parity claim.

If you do not want to operate the database, evaluate Kurrent Cloud. If you do operate it, its documented archiving and backup workflows may fit your storage policy. No managed Chronicle service is documented in this snapshot.

Ready-made connectors are another reason to choose KurrentDB. Sending events to Kafka, RabbitMQ or Elasticsearch through a server-side connector is a different responsibility from writing and hosting a Chronicle reactor yourself.

## Moving between them

Moving between the two is not a configuration change. They use different storage, different consumer and projection models, and different client APIs, so a migration touches application code and not only data.

The reviewed sources did not provide a migration guide in either direction. Plan for application changes, including how stream names map to event sources and how subscriptions become observers. If you want help planning a move, [ask the community](/community/).

## Questions to answer before choosing

1. Do you want a dedicated event database, or a server that also runs your projections and manages your reducers and reactors?
2. Which languages must read and write the history, and do their clients expose the operations you need?
3. Do you need ready-made connectors to external systems, or a managed service?
4. Will you run a cluster, and are the KLv1 terms for it acceptable?
5. How must personal data in events be protected and erased?

## Limitations

- This is a documentation comparison, not a benchmark or a production evaluation.
- We reviewed the pages linked here. KurrentDB may document more than we found, and its docs change independently of ours.
- KurrentDB 26.0 long-term support (LTS) and 26.2 short-term support (STS) differ in licensing and features; this snapshot compares 26.2.3.
- Client availability does not establish parity between clients.
