KurrentDB and Cratis Chronicle both store events in a separate server. KurrentDB owns its storage engine; Chronicle uses a storage database you choose. Their processing models also differ: decide where application views should live and who will maintain them.

The Cratis team wrote this page; Chronicle is our product. KurrentDB was formerly EventStoreDB. See the [.NET](/compare-event-sourcing-dotnet/) and [JVM](/compare-event-sourcing-jvm/) selection guides for other choices, and [our comparison method](/compare/) for scope.

## Choose KurrentDB or Chronicle

Choose KurrentDB when you want its stream database, subscription model, and connector infrastructure while choosing the application layer separately. Evaluate Kurrent Cloud if you want a managed database.

Choose Chronicle when you want the kernel to coordinate read-model production as well as event storage. Projections execute in the kernel; reducer and reactor handlers execute in connected applications. This page evaluates self-hosted Chronicle.

## Method and versions

Reviewed **2026-11-22** against [KurrentDB 26.2.3](https://github.com/kurrent-io/KurrentDB/releases/tag/v26.2.3), released October 19, and [Chronicle 19.181.2](https://github.com/Cratis/Chronicle/releases/tag/v19.181.2), released November 22. Release dates are not SDK publication dates. KurrentDB claims use its 26.2 documentation; Chronicle claims use the tagged sources linked below.

## Architecture: two servers

[KurrentDB](https://docs.kurrent.io/server/v26.2/quick-start/) stores events in streams in its own engine and provides gRPC client access. The [Chronicle Kernel](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/architecture.mdx) stores events through providers and coordinates observers. Both designs introduce a network boundary between application and event store.

An observer checkpoint or subscription acknowledgement does not make a consumer's external side effect atomic with the original append. Design duplicate handling and recovery around the actual consumer contract.

## Licensing

KurrentDB 26.2.3 uses [Kurrent License v1](https://github.com/kurrent-io/KurrentDB/blob/v26.2.3/LICENSE.md), which its [introduction](https://docs.kurrent.io/server/v26.2/quick-start/) identifies as not OSI-approved. It includes managed-service and license-mechanism restrictions. In **26.2**, single-node deployments no longer require a key for previously enterprise features; **every multi-node deployment requires a valid license** ([installation](https://docs.kurrent.io/server/v26.2/quick-start/installation.html)). Do not apply this key boundary to earlier release lines.

Chronicle 19.181.2 uses the [MIT license](https://github.com/Cratis/Chronicle/blob/v19.181.2/LICENSE). Adjacent products and managed offerings have their own terms; review the terms of the actual deployment.

## Consuming events and building read models

KurrentDB's [persistent subscriptions](https://docs.kurrent.io/server/v26.2/features/persistent-subscriptions.html) provide consumer groups, acknowledgements, retries, and parked-event replay. Delivery is at least once and ordering is not guaranteed. Catch-up subscriptions instead leave checkpoint ownership with the consumer.

KurrentDB's [projection documentation](https://docs.kurrent.io/server/v26.2/features/projections/intro.html) distinguishes the default V1 engine from opt-in V2 and its limitations. It recommends separate application read models for many workloads. Projection output streams, projection state, and external query stores are different artifacts; choose which your application needs.

Chronicle separates kernel projection execution from application-side reducer and reactor handlers. Its [HTTP webhooks](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/webhooks/index.mdx) are delivered by the kernel at least once, so receivers must tolerate duplicates. An HTTP receiver is not automatically a connector to every broker or database.

## Storage and hosting

KurrentDB offers [single-node, clustered, and cloud deployment choices](https://docs.kurrent.io/server/v26.2/quick-start/installation.html). Chronicle requires its kernel plus the selected storage. Chronicle's [SQL clustering](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/hosting/configuration/clustering.md) supports PostgreSQL and SQL Server as alternatives to MongoDB clustering. Nodes need shared cluster identity and database configuration. SQLite and in-memory storage do not support multi-node deployment, and in-memory data is ephemeral.

A read-model sink is a separate choice from the event-storage provider. Compare the [sink contract](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/sinks/index.mdx) with your query and recovery needs.

## Languages and clients

KurrentDB's [26.2 introduction](https://docs.kurrent.io/server/v26.2/quick-start/) lists supported Python, Node.js, Java, .NET, Go, and Rust clients, with Ruby and Elixir community clients. Chronicle has independently released [.NET/server 19.181.2](https://github.com/Cratis/Chronicle/releases/tag/v19.181.2), [TypeScript 6.67.7](https://github.com/Cratis/Chronicle.TypeScript/releases/tag/v6.67.7), [JVM 7.13.0](https://github.com/Cratis/Chronicle.Kotlin/releases/tag/v7.13.0), and [Elixir 3.25.0](https://github.com/Cratis/Chronicle.Elixir/releases/tag/v3.25.0).

A language list is not equal feature coverage. Check the operations and server pairing of the specific SDK before designing around a server capability.

## Compliance and personal data

KurrentDB's [redaction procedure](https://docs.kurrent.io/server/v26.2/operations/redaction.html) uses a support-provided local tool on each node to overwrite selected event data with blank bytes; metadata remains. Chronicle's [personal-data protection](https://github.com/Cratis/Chronicle/blob/v19.181.2/Documentation/compliance/index.md) encrypts marked values with a key per subject, which can be deleted to make those encrypted values unreadable.

Neither mechanism reaches every plaintext copy, export, read model, or backup automatically. Evaluate erasure scope and recovery policy separately; this comparison makes no regulatory-compliance claim.

## Where KurrentDB is the better choice

KurrentDB fits applications that want its stream and subscription contracts while keeping read-model consumers independent. Its supported language clients can settle an SDK requirement. Its [connector infrastructure](https://docs.kurrent.io/server/v26.2/features/connectors/features.html) may reduce application-owned integration work, and its [managed deployment](https://docs.kurrent.io/server/v26.2/quick-start/installation.html) is worth evaluating when operating the database is not your team's goal. Check destination availability and terms rather than assuming every connector has the same requirements.

## Moving between them

Migration touches application code as well as data. Map stream names to event-source identities, concurrency expectations, event schemas, subscription positions, and observer behavior. Rebuild a representative read model and rehearse recovery before changing the writer.

## Questions to answer before choosing

- Where should application read models live, and who rebuilds them?
- Can consumers tolerate duplicate or out-of-order delivery?
- Do you need a specific connector, SDK operation, or managed deployment?
- Which clustering configuration and license terms apply?
- How will personal-data erasure reach derived copies?

## Limitations

This is a documentation comparison, not a benchmark or production evaluation. It does not establish client parity, throughput, or operational reliability. Omitting a capability is not evidence that either product lacks it.
