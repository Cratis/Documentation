An Automation starts work without a user submitting a command. Here, a daily clock event prompts a Cratis Chronicle reactor to find uncollected Library reservations whose deadlines have passed. The reactor sends Cratis Arc commands to recheck each reservation and record its expiry, so other Library workflows can act on that outcome.

Choose the C#, Kotlin, Java or TypeScript backend example. The TypeScript backend is available from source, not npm. The [reactor table](#how-each-backend-runs-the-reactor) explains each backend's command execution and failure handling; the [series comparison](/scenarios/vertical-slices/#how-the-backends-differ) covers the wider setup.

- a queryable to-do list of reservations and their expiry dates

- a `ReservationExpired` event that marks a reservation as no longer valid
- a `CancelExpiredReservation` command that handles the cancellation
- a `ReservationExpiryReactor` that observes events and drives the process

## What is Automation?

In Event Modeling terms, an **Automation** slice answers the question: *"What should the system do on its own, without a human initiating it?"*

The shape is:

1. A read model acts as a **to-do list** — it contains items that the system needs to process
2. A **Reactor** watches the event stream
3. When the reactor sees a relevant event, it evaluates the to-do list and fires a **Command** for each item that needs action
4. That command produces another event, which closes the loop

Automation uses the same building blocks as State Change and State View. Here, Chronicle supplies event observation and Arc supplies the command pipeline through the optional Arc–Chronicle integration. Time passing is not itself an event: the scheduler must append `DailyTick` for the automation to run.

A daily sweep is appropriate when releasing a reservation on the next sweep is acceptable. If the Library needs cancellation at the exact expiry time, use a more frequent or per-reservation trigger. Observer retries can repeat work, so command execution and any external effects need deliberate retry handling.

## Domain context

The Reservation slice supplies the events that open and close a reservation. The events refer to the member by `MemberId`, the GUID-backed member identity from `Members/MemberId`. This series declares it with the member registration slice in the [Translation tutorial](/scenarios/vertical-slices/translator/#step-1--the-member-registration-slice), which comes next; if you are working in order, copy that declaration now. Give the reservation and ISBN their own domain types. The reservation events belong to the same reservation event source, so their own reservation ID comes from event context. `MemberId` identifies a related entity and belongs in the payload.

A `BookReserved` event establishes the deadline. Collection (`BookBorrowedFromReservation`), cancellation or expiry closes the reservation. This slice records `ReservationExpired` when an uncollected reservation is due; updating inventory in response is a separate workflow, not implemented here.

### What is happening here?

`PendingReservation` supplies the cancellation decision with the reservation's current state. It is a passive [read model](/chronicle/read-models/): Chronicle computes it from events on demand by reservation key instead of maintaining it proactively. `BookReserved` supplies its properties, and any of the three closing events removes it. It is an internal command dependency, not a frontend query.

The reactor needs a list to sweep, so `ReservationDueForExpiry` is an active, stored read model. It follows the same opening and closing events, but keeps only the identity and deadline needed to find candidates. C# reads its MongoDB collection, TypeScript uses the reactor's `services.readModels`, and Kotlin and Java use Chronicle's read models.

The sweep needs each reservation's ID in the model; Kotlin and Java mark `id` with `@FromEventSourceId` so the projection copies the event-source ID into it.

:::note[Kotlin and Java need Chronicle.Kotlin 6.8.0 or later]
Both JVM read models rely on projection instances being keyed by their event source. Use a client with the event-source projection-key fix introduced in Chronicle.Kotlin 6.5.0; older clients could collapse instances onto one empty key ([background](https://github.com/Cratis/Chronicle/issues/3924)).

The `Instant` times in the events and read models need 6.8.0, which serializes `java.time` values as ISO-8601 strings. Earlier versions wrote them as JSON objects, and Chronicle rejects such an append against the event's schema.
:::

`CancelExpiredReservation` provides the current time before its handler runs, letting a direct decision spec supply a fixed timestamp instead. The Arc–Chronicle integration resolves `PendingReservation` by the command's `ReservationId`. The handler accepts a missing model through a nullable parameter in C# and Kotlin, `commandReadModel(PendingReservation, { optional: true })` in TypeScript, or `Optional` in Java.

A pending reservation expires when its deadline is at or before `now`. Missing or not-yet-due reservations produce no event, but the command result differs: C# returns an explicit validation error, while Kotlin, Java and TypeScript return no event as a successful no-op. The C# reactor deliberately tolerates those validation rejections when sweeping stale candidates.

The sweep list can lag behind the event log, so it only nominates candidates. The command rechecks each reservation when it runs, without trusting the earlier collection query, and decides whether it may expire. Read-model injection alone is not a blanket guarantee against a concurrent collection or cancellation; a production lifecycle needs append-time rules or the applicable [consistency controls](/arc/backend/csharp/chronicle/commands/transactional-commands/) for competing terminal transitions.

The [reactor](/chronicle/reactors/) handles `DailyTick` only after a scheduler or background service appends it to the application's event log. It does not create a timer. If the to-do projection has not caught up, a later tick can find a reservation that was absent from an earlier sweep.

Each cancellation goes through Arc's command pipeline, including validation and authorization. Decide which rejected commands are expected and which must fail the tick. The C# example tolerates its business validation rejections but throws on authorization failure or exceptions. The JVM examples and TypeScript result handler throw on any unsuccessful command result.

The reactor has no original HTTP principal. The C# and TypeScript commands here have no authorization rules, and the Kotlin and Java commands are marked `@AllowAnonymous` to match. If these commands require authorization, configure a deliberate execution context: in Kotlin, Java and TypeScript, the reactor's `@ExecuteCommandsAsSystem` or `@executeCommandsAsSystem` marker gives its commands a system principal with the roles you list.

### How each backend runs the reactor

This is the first reactor in the series; the [Translation tutorial](/scenarios/vertical-slices/translator/) uses the same mechanics.

| Mechanism | C# | Kotlin and Java | TypeScript |
| --- | --- | --- | --- |
| Reactor | An `IReactor` | A `@Reactor` class | A `@reactor()` class |
| How Chronicle finds the handler | Supported signatures and event parameter types | The event parameter type | The method name: the event class in camelCase (`dailyTick` for `DailyTick`) |
| How the commands run | The reactor calls the constructor-injected [`ICommandPipeline`](/arc/backend/csharp/commands/command-pipeline/) | The reactor passes each command, its own type and the event context to Arc's [`ChronicleCommandSideEffectHandler`](/arc/backend/kotlin/guides/chronicle/#execute-reactor-command-side-effects) | The handler returns the commands, and Arc's [`reactorCommandResultHandler`](/arc/backend/typescript/chronicle/reactors/command-side-effects/) runs them in order |
| How a failed command fails the handler | Throw `ReservationExpiryFailed` when `!IsAuthorized` or `HasExceptions`; tolerate validation rejections | Check `isSuccess` and throw the named exception | The result handler stops at the first unsuccessful command result and fails the handler |
| Once-only marker (Step 2) | `[OnceOnly]` | `@OnceOnly` | `@onceOnly()` |

Returning an unsuccessful command result does not by itself fail a reactor that calls the pipeline directly. The C# and JVM examples inspect the result and throw for the failures described above, making them visible to Chronicle.

The TypeScript handler receives the stored event as parsed JSON, so it converts `occurredAt` back to a `Date`. `withChronicle` installs `reactorCommandResultHandler` for a client Arc creates; a Chronicle client you create yourself needs it as its `reactorResultHandler` option.

## Step 2 — Idempotency with once-only handlers

The once-only marker on the daily-tick handler skips the method during replay. Rebuilding projections should not execute today's cancellation logic for every historical clock tick. The projections still consume the recorded `ReservationExpired` events to rebuild their state.

The marker controls replay, not exactly-once delivery. A failed tick can run again after earlier cancellation commands succeeded. When a command sees a recorded expiry, it appends nothing further: C# returns the missing-reservation validation error tolerated by this reactor, and the other examples return no event. External effects, such as releasing a copy through another service, need their own stable idempotency key or equivalent duplicate handling.

## Step 3 — Error handling

If the daily-tick handler fails, Chronicle's observer failure and recovery policy applies. Earlier successful cancellation commands are not rolled back as a group. Monitor failed partitions and repair or retry the underlying operation; do not swallow the failure.

Keep an already closed reservation out of the append path, whether the command reports a no-op or an expected validation rejection. Match the reactor's result check to that choice. An authorization or infrastructure failure must remain visible rather than being mistaken for a stale candidate.

Test the decision with a fixed `now`: a missing reservation, deadlines before, at and after that time, and each of the three closing events. Assert the command result as well as the absence or presence of `ReservationExpired`. Then exercise scheduler delivery, projection catch-up and a partial-sweep retry together in a hosted test. Replay and retry are different paths; the once-only marker only addresses replay.

<Recap>

1. The scheduler's `DailyTick` wakes `ReservationExpiryReactor`, a [Chronicle reactor](/chronicle/reactors/).
2. The reactor sweeps `ReservationDueForExpiry`, the active, internal [projection](/chronicle/projections/) that nominates candidates, and sends `CancelExpiredReservation` for each through the [Arc](/arc/) command pipeline.
3. That model-bound command reads the passive, internal `PendingReservation` projection as its command-side read model, decides whether the reservation expires and, if so, records `ReservationExpired`, a Chronicle [event type](/chronicle/events/).

Every expiry is recorded as an event, so later views and automations can follow the outcome without repeating the deadline logic.
